# 2026-09-23 状态缺口与系统时钟诊断

## 结论

1. 状态时间缺口不是单纯由原始数据写盘造成；无媒体写盘、跳过图像读取后仍可复现。范围缩小到SDK状态更新/缓存及其上游，但尚不能认定硬件丢帧。
2. G1的系统时间确有毫秒级动态变化；不是单纯的组帧规则误拒收。发现systemd-timesyncd与phc2sys同时运行、目标均涉及系统时钟，竞争调时是优先验证的原因，尚未通过停用对照确认因果。
3. 头部今日恢复15Hz的原因未定。G1本次开机时间约08:52:47，不能排除重启因素，不能仅归因于补光。

## 时间同步服务线索

只读查询发现：

- systemd-timesyncd使用192.168.1.99（PC）为NTP源，轮询32秒；状态查询上报offset约-79ms。
- ptp4l运行于eth0，配置slaveOnly=1、domainNumber=11。
- phc2sys命令为`/usr/sbin/phc2sys -s eth0 -c CLOCK_REALTIME -O 0 -S 1`。
- 09:01:04 phc2sys报告PHC偏差75711ns；09:01:05变为-6954297ns；09:01:06变为-8164834ns。
- 同时ptp4l master offset仍在数百ns量级，偏差主要出现在系统时间相对PHC这一层，与09:01:05–06跨机映射拒收时段吻合。

证据：g1_clock_status.txt、time_services.txt、ptp_evidence.txt。双重调时具有强相关证据，仍需受控停用验证；不声称已唯一确认所有缺口均由此导致。

## 待确认的可恢复对照方案（尚未执行）

这是整机系统时间服务变更，影响范围超出数采程序；需先确认机器人静止且没有其他控制或采集任务。

1. 保存systemd-timesyncd、ptp4l、phc2sys活动状态，设置独立于SSH连接的自动恢复措施。
2. 临时停止systemd-timesyncd 90秒；保持当前PTP链路运行，保留服务启动配置。
3. 前30秒观察收敛，后60秒每0.2秒采集三种时钟及跨机往返时间，同时读取phc2sys日志。
4. 无论测试成功或失败，恢复systemd-timesyncd原活动状态并核验；保留全过程记录。
5. 对比偏移峰峰值、每秒变化、RAW差值及映射拒收数量，判断周期性约7–12ms扰动是否消失。观察不到扰动下降则不将NTP/PTP竞争确认为根因。
6. 时钟稳定后，另做上游状态主题与SDK同时读取，判断状态缺口是否仍存在，再安排相机共同标记验证和带动作采集。

这次不修改相机参数、不重启机器人、不启停上述时钟服务；现有数据保持training_ready=false。
