# G1 采集环境隔离决策

建议：做应用与数据隔离，初版先复用已验证的系统 Python 3.8.10 和厂商 aarch64 SDK 1.9.0。G1 只负责轻量原始记录，不在机器人上安装完整 LeRobot/PyTorch/视频训练环境。PC 继续使用固定的 amd64 LeRobot 镜像。

## 第一版部署约定（待实现，未创建远端目录）

- 程序版本独立目录，例如 `/home/galbot/vla_capture/releases/<version>/`。
- 会话日志与数据分别放在 `/home/galbot/vla_capture/logs/`、`/userdata/vla_capture/sessions/<session_id>/`；不覆盖厂商日志和配置。
- 启动脚本只在子进程中加载 SDK setup 与必要环境变量，设置 `PYTHONNOUSERSITE=1`，不修改 `.bashrc`、全局 PATH、系统 Python 或厂商 setup.sh。
- 使用普通用户 galbot，独立进程，明确记录器 PID/会话；退出仅清理自身 SDK 客户端及文件，不停止厂商传感器服务或控制服务。
- 初版尽量只用 Python 标准库＋现有 SDK，保存 SDK 原始 JPEG/深度字节，复杂压缩、解码和 LeRobot 转换在 PC 完成。
- 队列必须有界，统计内存、CPU、磁盘和待上传积压；记录线程不能阻塞控制线程。进程隔离或 venv 本身不保证实时性与 CPU/磁盘资源隔离。

## 何时需要 venv

新增 Python 依赖时建立独立 Python 3.8 venv，固定版本并验证 SDK 导入/连续读取。SDK 依赖若必须复用系统包，可评估 `--system-site-packages`，但该选项会暴露系统包，因此不是完全依赖隔离。避免升级会遮蔽 SDK 所需 ABI 的 NumPy 等基础包；厂商动态库仍通过受控环境路径加载，venv 不会自动隔离它们。

目前没有必须新增的依赖，也没有实际创建 venv；优先使用已实测路径，待记录器依赖明确后决定是否增加虚拟环境。

## 容器化

当前 PC 镜像为 amd64，不能作为 G1 的原生 aarch64 环境直接复用。G1 Docker 化留作后续单独工程项，需要验证 Jetson/L4T、SDK 动态库、DDS/共享内存、设备访问及长时间性能；不作为第一版可靠原始采集的前置要求。

依据：[Python venv 官方说明](https://docs.python.org/3.11/library/venv.html)。本方案未执行远端安装、环境修改或服务部署。
