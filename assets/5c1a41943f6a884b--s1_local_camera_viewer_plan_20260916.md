# S1 全相机本地实时查看实施计划

日期：2026-09-16。状态：仅规划，未连接机器人、未部署或启动查看器。
用户拟交由 Luna max 实施；本文不构成真机访问或运动授权。

## 1. 目标与范围

在本地电脑一键打开多画面查看器，实时查看 S1 当前实际可用的全部相机流，
包括 RGB、原生深度以及已启用的 IR；能在用户自行运行 Mode 00 时独立旁观。
每路显示名称、在线状态、实际 FPS、源时间戳、停更状态和分辨率。
深度显示固定米制色标、无效值及鼠标位置的公制深度；支持单路放大。
查看器停止、崩溃、断网不得控制或停止主业务。

首期候选清单（以部署版本和只读盘点结果为准，不按枚举数量宣称全部在线）：

| 位置 | RGB | 原生深度 | 可选 IR |
| --- | --- | --- | --- |
| 头部 | HEAD_LEFT_CAMERA、HEAD_RIGHT_CAMERA | 不预设已有深度输出 | 不预设 |
| 左腕 | LEFT_ARM_CAMERA | LEFT_ARM_DEPTH_CAMERA | LEFT_ARM_INFRA_CAMERA_1/2 |
| 右腕 | RIGHT_ARM_CAMERA | RIGHT_ARM_DEPTH_CAMERA | RIGHT_ARM_INFRA_CAMERA_1/2 |

当前 S1 `1.9.0` 运行库因重新导出通用 `SensorType`，也能看到
`LEFT/RIGHT_FRONT_SURROUND_CAMERA` 和 `LEFT/RIGHT_REAR_SURROUND_CAMERA` 四个
名称；它们在 S1 专用相机说明中没有出现，且在本机逐个及分组初始化均返回
`init_ok=false`。这些是通用/G1 候选，不能当作 S1 物理相机或纳入实施目标。
因此当前 S1 基线是 4 路 RGB + 2 路腕部深度。当前运行库没有暴露计划表中的四个
IR 枚举，IR 只保留为版本差异待验证项，不能按粘贴页面直接调用。
用户所说“所有”通过实机清单闭环：每项标记在线、未启用、版本不支持或读取失败，
并记录依据。存在额外相机时加入清单；没有数据时不偷偷改配置或启动驱动。
文档指出某些版本的 IR 需要 `ir_enabled=true`，不可把空数据一律归因网络。
头部 FoundationStereo 深度、LingBot 补全、点云及录像均非首期必需项。

## 2. 已有依据与待验证项

- 本次本地可见 `/opt/ros/humble`；历史项目已使用 Humble/RViz2。
- 三路 LiDAR 已有被动 embosa reader → SSH → 本地 ROS 2/RViz 的实现。
  这证明项目中已有桥接经验，不证明相机协议和多路性能已经验证。
- 左右腕 RGB-D 曾完成 1280×720 冻结采集；当前全相机在线性、帧率待验证。
- 用户粘贴 SDK 文档定义 RGB/depth/IR getter、压缩数据、时间戳与相机内参。

  因此不能把用户给出的命令作为相机测试命令运行；本轮没有核验远端新版本。
- 既有 TSDF reader 曾出现可观 CPU/RSS 成本，因此“只读”和“低开销”须分开验证。

## 3. 推荐架构与路线选择

```text
S1 已有相机数据生产者
  → 独立只读采集进程（按实际接口选择 SDK getter 或被动 reader）
  → 有界压缩图像流，经 SSH 传输
  → 本地接收/解码 → 本地 ROS 2 标准图像话题
  → 多画面查看器；RViz2/rqt_image_view 可独立订阅
```

优先复用已有 RGB-D 解码/采集代码，以最小传感器集合初始化独立 SDK 进程；
先审查初始化、退出语义与 Mode 00 并发读取，不调用控制器权限或运动接口。
若 SDK 初始化有不合适的全局副作用或负载，再评估被动 embosa reader。
复用 LiDAR 的传输和清理思路，不假定相机使用相同消息类型/协议。

若盘点发现已经提供标准 ROS 2 Image/CompressedImage 端点，且类型、网络和
QoS 均兼容，可采用直接订阅作为更简单的路径。仅使用 DDS、protobuf 字段相似
或文档称“兼容 ROS 消息”不等于能直接 `ros2 topic` 订阅。
首期不要求在机器人安装 ROS 2，也不把机器人控制网络直接扩展到本机 ROS 域。
本地 ROS 使用独立 domain、仅本机发现；SSH 是跨机数据通道。

多画面优先在本地做轻量 ROS 订阅面板，保存布局，另提供 RViz 配置。
不把“能用 rqt 看单路”当作全路同屏目标已完成。

## 4. 数据与性能约束

- RGB/IR 尽可能原样转发已有压缩负载，避免机器人重复解码/编码。
- 深度保留原始数值、format、depth_scale、尺寸、源 timestamp/frame_id；
  先核验压缩头与解码方法，再转为标准 Image。不能只传伪彩图或用 JPEG 编码深度。
- 粘贴文档语义为 `meters = pixel_value / depth_scale`，以实机版本复核结果为准。
  本地标准化为 32FC1 米，或确认毫米语义后的 16UC1；不将任意 scale 冒充毫米。
  不盲目将普通 PNG 字节标为 ROS compressedDepth：必须验证插件头和实际格式。
- 发布匹配的 CameraInfo；缺失标定应明确标注，不编造 K、D、R、P。
  RGB 与深度是否对齐由元数据/现有采集实现核验，不能只看尺寸相等。
- 全分辨率接收、在本地缩略显示；需要机器人端缩图时另测编码负载，并正确更新内参。
- 每路仅保留最新帧，有界帧大小/缓存、发送超时、公平调度、慢消费者丢旧帧，
  单路失败不阻塞其他路。重复源时间戳不计作新帧；流协议日志走 stderr。
- ROS 图像采用与订阅者兼容的 sensor-data QoS、小队列；按实际端点测试。
- 起步 2 FPS/路，稳定后目标 5–10 FPS/路，单路选看可进一步提高。
  30 FPS 全路不是承诺。先量实际每帧字节数再定网络预算。
- 示例：若 4 RGB（每像素 3 B）+2 depth（2 B）均为 1280×720，10 FPS
  未压缩约 147.5 MB/s，即 1.18 Gbit/s，尚不含协议开销；实际头部尺寸待核验。
- 显示源时间和本地最后接收间隔。跨机时钟未同步时不把二者相减宣称端到端延迟；
  需报告时钟偏差/同步依据，否则仅报告本地接收至显示延迟。
- 各路独立实时显示，不等待所有相机同步；腕部 RGB/depth 配对显示时保留时间差，
  不将不同帧当作同帧测量。超过 1 秒未收到新帧标 stale，旧画面须显著标记。

ROS 官方依据：
[Humble QoS](https://docs.ros.org/en/humble/Concepts/Intermediate/About-Quality-of-Service-Settings.html)、
[compressedDepth](https://docs.ros.org/en/humble/p/compressed_depth_image_transport/generated/namespace_compressed_depth_image_transport.html)。

## 5. 分阶段实施与交付

1. **本地代码审查及离线样机**：阅读仓库规则和上述参考，检查已有 live_capture
   与 ROS 包；用冻结 RGB-D/合成缺帧源完成解码、深度单位、停更、队列和面板。
   产出候选接口表与离线演示，不启动远端程序。
2. **获得当前实机访问授权后只读盘点**：核验机器人身份、SDK/运行环境、生产者、
   相机配置和可用接口，生成 inventory。逐路短时取样，记录真实编码、scale、
   frame、尺寸、FPS 和 CameraInfo。不要启动 Mode 00、重启服务或改 IR 配置。
3. **右腕 RGB+depth 最小链路**：复用已验证采集路径，从 2 FPS 开始，
   完成本地 ROS 发布、显示和像素深度比对；记录 CPU/RSS/带宽与清理结果。
4. **扩展所有已启用流**：加入左腕和头部，再加入已启用 IR。
   完成六宫格/扩展布局、放大、每路状态与参数化限帧，隔离失败流。
5. **并行兼容性验证**：先静止观察 10 分钟；若用户已有独立授权并自行运行
   Mode 00，只旁观该运行并记录查看器启停前后已有业务指标。
   不为验收自行执行一键脚本。记录主流程取图超时、阶段耗时和资源增量，
   无有效对照时标为“业务影响待验证”，不能宣称零影响。
6. **一键入口与文档**：交付本地启动/停止、配置、inventory、RViz/面板布局、
   测试报告和故障处理。关闭仅清理本次拥有的进程/reader/SSH；不误关共享连接。
   修改当前事实时更新知识库，保留失败实验。

建议新实验目录：`experiments/20260916_s1_camera_viewer/`。
ROS 集成沿用规范包 `experiments/20260822_s1_rviz_demo/ros2_ws/src/s1_rviz_demo`，
新增独立相机 launch/config，避免修改现有 LiDAR 默认行为或创建第二套导航包。
启动入口必须显式区分 offline/live；离线默认不建立 SSH。

## 6. 验收标准（工程目标，未实测）

- 所有实机盘点项都有状态和依据；全部已启用可读相机可同时查看。
- 6 路基线存在时，目标每路 ≥5 FPS 连续 10 分钟；源帧率不足须如实记录。
- 同步时钟条件下端到端 P95 目标 ≤500 ms；否则单列本地延迟与未知部分。
- 静态画面也能识别源帧是否更新；断网 1 秒后明确 stale，重连有界且不积压旧帧。
- 原始深度解码及缩放有冻结样本逐像素核验，伪彩图色标固定、无效值可辨。
- 初始资源预算：新增远端进程总 CPU 平均 ≤1 个逻辑核、RSS ≤500 MiB，
  持续网络 ≤实测可用带宽的 20%；不达标先降帧/减订阅并报告，不强行常驻。
  若 SDK 固定开销超预算，明确原因与替代方案后再调整预算。
- 有可比运行时，主流程相关阶段耗时增幅目标 <10%，无新增取图超时；
  没有独立授权运行 Mode 00 时该项保留待验证，不因验收触发运动。
- Ctrl+C、异常退出、网络中断均验证 reader/子进程清理；不发送控制或 shutdown
  整机命令。SDK 生命周期清理方法须核验仅作用于本进程后才使用。

## 7. 可交给 Luna max 的任务说明

按本计划实施 S1 本地全相机只读查看器，先完成本地审查和离线功能，再在用户
明确授权当前 S1 访问与采集后进行短时在线验证。独立于 Mode 00，不运行
`run_s1_mode00_one_click.py`，不获取控制器、不控制头/双臂/夹爪/升降/底盘、
不自动开启 IR、不修改生产相机配置、不调用 SAM3/LingBot/FoundationStereo。
只读查看器本身预期无物理运动；与其他任务并行时仍须评估额外算力/网络负载。
实机运动不在本任务范围，任何后续动作必须按 AGENTS.md 单独说明风险并逐步确认。
不要修改 third_party 或覆盖已有用户改动。完成后给出一键命令、可用流清单、
实测性能、业务影响证据、未完成项及清理验证；不能以离线测试代替在线验收。
