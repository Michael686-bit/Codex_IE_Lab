# G1 模型控制：实时预览、单次动作、短程闭环

当前默认运行结构是PC的两个独立容器：GPU模型服务和Galbot PC SDK控制程序。G1沿用现有SDK服务。模型控制无需GP001、主臂数据或遥操启动程序；仅复用SDK轨迹构造、反馈读取和限位函数。

## 第一阶段：实时预览

```bash
bash g1_policy_control/run_pc.sh --mode preview --channels arm --seconds 10
```

入口会先取得与已有控制程序相同的宿主机锁，再只读核对机器人部署URDF哈希、重新估计PC/G1时钟偏移，然后进入SDK容器。机器人地址默认192.168.1.88；变更时显式设置 `G1_ROBOT_HOST`，同时确保PC SDK peer配置一致。没有关闭SSH主机密钥检查，也不会修改网络或机器人服务。

预览只启动传感器SDK进程，不启动运动/停止SDK进程，不发送手臂、夹爪或停止命令。终端显示接受/拒收次数、原始预测检查后的拟发送目标与时延。越界预测记录后继续预览；传感器输入持续缺失或SDK RPC超时会结束运行。

预览验收：完整运行、至少10次预测接受、输入和预测拒收均为零、运动接口调用数为零、SDK清理确认且进程正常退出。`preview_validation_passed` 汇总这些条件；它不代表真机运动或任务成功验收。任何过期输入、预测越界或超时都继续按原保护拒收。

## 第二阶段：单次受限动作

先验证仅手臂：

```bash
bash g1_policy_control/run_pc.sh --mode step --channels arm --seconds 5 --execute
```

完成预检后显示实测姿态、模型预测和拟执行的受限目标；显式 `--execute` 即表示启动运动，预检完成后直接开始，不再要求输入 `ARM`。只调用一次正常手臂目标发布，观察一个轨迹周期后停止并检查停稳反馈，然后退出。夹爪不发送正常指令，也不发送保持指令。

手臂单次通过后，再验证仅夹爪：

```bash
bash g1_policy_control/run_pc.sh --mode step --channels gripper --seconds 5 --execute
```

只发送一次正常夹爪目标；结束时若反馈有效，会额外发送当前开度保持请求。不能把这次保持请求误计为第二次模型动作。手臂不发送轨迹或停止命令。

单次模式强制一个动作段，累计目标预算不超过每关节0.5°、夹爪2mm。默认速度上限0.05rad/s、夹爪0.02m/s。预算只是目标约束，实际位移与速度仍需通过真机反馈验收。

## 第三阶段：短程闭环

仅在手臂单次动作及停止检查通过后，先运行三次动作以内的短程：

```bash
bash g1_policy_control/run_pc.sh --mode closed-loop --channels arm \
  --seconds 2 --max-commands 3 --max-joint-travel-deg 2 --execute
```

每步取执行后的新观测，再预测并执行首步。时间、动作次数、每关节相对起点的累计目标位移三者共同约束，任一耗尽即停止。若需逐步增加动作次数，保持相同权重与配置，并按真实结果决定。首轮不启用both通道，不直接运行完整抓放。

输入STOP并回车或Ctrl+C，停止事件独立于模型推理处理；迟到预测不能继续执行。停止动作由独立、预先初始化的SDK进程发出，不等待传感器读取锁。SDK响应超时会终止对应工作进程，禁止消费迟到响应。

停止请求接受与停稳分别记录。停稳验证要求多次推进的关节/夹爪时间戳、低速度和低位置漂移；无法确认会记录为失败。进程隔离仍不能保证机器人SDK服务器自身挂死时完成物理停止，现场物理急停须保持可用。

## 运行配置和日志

- `configs/validation.json`：本轮低速参数。`configs/g1.json`保留旧配置，不作为新CLI默认值。
- `configs/pc.json`：PC SDK路径模板。入口会生成带本次时钟偏移的runtime.json，不沿用旧104ms。
- `configs/models.json`：模型/权重注册表；切换需结束旧会话并重新预检，不支持运动中热切换。
- `run_pc.sh --dry-run`：只查看PC入口说明，不连接机器人。

每轮独立目录：`lerobot_runs/model_时间_PID/`，包含runtime.json、只读预检证据、events.jsonl和report.json，以及sdk_logs和sdk_native_logs底层日志。已有日志不会覆盖。入口结束时自动生成报告；也可手动分析：

```bash
python3 -m g1_policy_control.report /absolute/path/events.jsonl
```

报告区分正常动作、停止/保持、SDK请求尝试、SDK确认、停稳结果和模型拒收原因；不能将SDK确认直接视为任务成功。预览与真机执行使用不同标记。

本版未添加自碰撞或环境避障检查。限位与小位移不能证明不会碰撞。当前控制范围是左臂/左夹爪，其他关节运动会被反馈保护拒绝。

## PC 接收与 SDK 生命周期

当前主机已安装 `/etc/sysctl.d/90-g1-policy-receive.conf`，对应项目内同名配置文件：IP分片重组缓冲128MiB、残片保留3秒、UDP接收缓冲上限16MiB。2026-10-09对照确认原4MiB分片缓冲耗尽会使真实数据停止更新。启动预检只读取并核对配置，不能通过放宽数据时效绕过网络问题。原值与回滚依据保存于 `reports/g1_sdk_debug_20261009/network_sysctl.json`。

## 采集与推理时效

观测工作进程在初始化等待、模型推理、等待IPC请求和等待IPC请求期间持续轮询启用相机。腕部缓存仅匹配完全相同的真实源时间戳，且每次必须推进；不替换时间戳、不插值、不复用历史配对。

validation.json预留220ms给推理，因此选取的深度帧年龄最多80ms。选定腕部帧前也检查其他RGB和六维力的新鲜度，最多等待250ms获取满足条件的观测集合。六维力同样预留220ms推理时间，并留5ms采集处理余量；保留被选中样本的原始数值和源时间戳。推理结束后仍执行原300ms深度/六维力与600ms RGB时效检查，以及500ms预测和600ms看门狗限制。预留预算不保证任意GPU并行负载下都能通过；迟到结果必须丢弃。

模型服务使用单一持久推理线程处理reset和predict，HTTP请求线程不直接执行模型。同一输入在离线对照中的原始输出完全一致；实际速度以运行日志为准。

## 异步改造：只读影子验证（2026-10-12）

当前异步入口只构造参考轨迹和 SDK 消息，不发布轨迹，不提供 `--execute`。

## 用户执行的确定性轨迹测试入口（2026-10-13）

`--trajectory-test` 使用固定周期的确定性参考，先独立验证 SDK 发布与覆盖衔接。
它不调用 VLA 模型服务或相机，也不发夹爪命令。默认只读预览；只有在用户本地交互终端明确加 `--execute` 才会发布左臂轨迹，无额外 ARM 输入。

当前硬范围：单个左臂关节、目标幅度绝对值 0.1～0.8°、总时长2～3秒、相对起点位移保护上限不超过1°。
默认 J7 以最小 jerk 曲线在1.5秒内到达+0.8°，随后1.5秒返回起点。
发布参考周期50 ms，每个SDK消息覆盖最多100 ms，跨往返拐点时保留边界点；全部关节位置/速度/加速度显式赋值。
3秒默认轨迹的解析最大速度0.01745 rad/s、加速度0.03583 rad/s²、jerk0.24823 rad/s³，低于现有0.05、0.3、2.0限制。
