# G1 采集时间戳与部署方式复测

日期：2026-09-20，约 10:16–10:24（北京时间）。

**结论：可以采集，但必须保留源时间戳、缓冲并对齐。推荐 G1 本地可靠记录原始数据，通过现有千兆有线连接分 episode 传到 PC，由 PC 做对齐、LeRobot 转换和训练。PC 经有线直接落盘也具备带宽条件，但尚未通过长时间真实录制验收；不建议走当前 Wi-Fi 直接录全量数据。**

## 测试范围和边界

- 目标：galbot-echo，原 SSH 地址 10.34.216.136；确认同一机器有线地址 192.168.1.88。使用同一已知主机密钥验证有线 SSH。
- 机器人刚开机：初查 uptime 约 3 分钟。传感器复测为一次 60.003 秒窗口，SDK 预热 4 秒；覆盖 8 路 RGB、2 路深度、左右腕力、5 组关节及左右夹爪，共 19 个数据流。
- 只读 SDK 客户端，不发运动命令、不修改机器人/相机配置、不修改 NTP 或路由、不启停机器人服务；SDK 正常清理退出。
- 所有流均有持续变化的时间戳，未报空数据或读取错误。本轮主测时间戳，不重复上次图像质量验收。
- 按源时间戳去重；低维状态约 4 ms 轮询，图像约 12 ms 调度轮询，SDK 同步接口约 10 Hz 检查，实际取得 589 组。所有调用共享一个循环，调度停顿和 latest-cache 覆盖也会造成漏取；观测频率不等于硬件额定频率。
- SDK 时间戳含义尚未通过独立硬件触发验证。这里的“对齐误差”指软件提供的源时间戳差，不等于已证明的实际曝光/物理测量误差。

观察到腕力/夹爪时间戳偶尔领先 G1 本机读取时间约 10.7 ms，关节约 9.9 ms，腕相机约 6.7 ms。负年龄不可能是负传输延迟，说明还存在源时钟/时间戳语义的偏差，不能声称本次已经验证物理同步精度达 4.5 ms。G1 wall−monotonic 在该 60 秒窗口整体变化约 0.003 ms，但这不证明控制器/相机等上游时钟与 G1 wall clock 完全一致。

左腕曾观察到约 134 ms 帧间隔，环视约 200 ms，低维反馈约 77–82 ms。可能包含读取漏帧、SDK 缓存或生产端停顿；本轮无法归因。不应跨这些缺口无条件插值，更不能把重复旧帧伪装成新帧。

**跨 PC/G1 时钟：** 两边 NTP=yes / NTPSynchronized=yes，但并未达到毫秒级一致。PC eno1=192.168.1.99，运行 chrony；G1 eth1=192.168.1.88，systemd-timesyncd 的 NTP 源就是这台 PC。G1 刚开机尚在收敛：读取的服务 offset 曾为 +77.6 / +61.1 / +52.8 / +44.5 ms，jitter 约 20–37 ms。

四时间戳 SSH 往返测量估计 G1−PC：无线测量中的一次最低 RTT 样本约 −102.57 ms，网络往返不对称带来的区间为 [−104.50, −100.63] ms；稍后有线最低 RTT 样本约 −30.72 ms，区间 [−30.87, −30.56] ms。有线一段约 8 秒内偏差还从 −33.05 ms 变化到 −28.67 ms，说明不能用一次性常数修正整个会话。区间假设单次交换期间没有时钟跳变且单向延时非负，不覆盖所有测量误差。

两组测量在不同时间进行；偏差减小不能归因于换了网线。应等待 NTP 收敛并持续测量；episode 中使用 monotonic 跟踪间隔，同时记录源时间戳及 wall/monotonic 映射。PC 生成的遥操指令要保存 PC 创建、G1 接收/下发时间及序号，不能用事后到达 PC 的时间作为动作发生时间。本次没有触发遥操动作，因此实际动作链延迟未验证。

## 有线与无线网络实测

发现现有千兆有线链路已经接通，PC eno1 与 G1 eth1 都报告 1000 Mb/s。访问地址会决定路径：10.34.216.136 走 wlp7s0/wlan0；192.168.1.88 走 eno1/eth1。不需要修改默认路由即可针对数据连接使用有线地址。

| 项目 | Wi-Fi：10.34.216.132→10.34.216.136 | 有线：192.168.1.99→192.168.1.88 |
|---|---:|---:|
| 32 MiB RAM→PC SSH 下载吞吐 | 9.63 MB/s | 113.71 MB/s |
| 下载前 RTT P95 | 56.26 ms | 1.10 ms |
| 下载后 RTT P95 | 54.02 ms | 1.10 ms |
| 下载后 RTT 最大 | 264.29 ms | 1.35 ms |

测试使用同一 32 MiB 随机负载，关闭 SSH 压缩。下载前后各 80 次四时间戳交换，排除第一组首个包含 SSH 建连时间的样本。吞吐只测内存/SSH/链路到 PC 管道，没有真实相机编码或磁盘写入；0.295 秒有线突发测试不是长期稳定吞吐验收，更不等同于 DDS 或正式 recorder 性能。

|---|---:|---:|
| 头左 RGB＋双腕 RGB | 6.67 MB/s，约 53 Mb/s | 约 24 GB |

上述估算未计协议、索引及磁盘开销，会随画面和压缩设置变化。Wi-Fi 对 3 RGB 的平均值虽可能承载，但余量小且有长尾，不宜作为正式数据唯一通路；全 RGB 或加双深度已超过本次 Wi-Fi 实测。千兆有线对 3 RGB 余量充足，全量也在短测带宽以内，但约占实测吞吐 67%，仍需持续采集、并发控制及写盘压测。

G1 本地约 1.5 TB 可用空间，内存约 62.8 GB，复测期间 vmstat 短采样 CPU idle 69–74%，有运行轻量记录器的基础。本轮没有做磁盘 fsync/持续写入压测，也没有启动多路编码器，不能据此承诺全量长录无掉帧。完整 SDK 同步缓存会占用额外内存，正式程序需要有界队列。

## 对采集与训练的影响

- 直接把“这轮读取到的最新图像、关节、力”拼一行，会带来腕力约 83 ms、环视约 191 ms 的 P95 错位。这是训练标签问题，不只是界面显示晚。
- 举例：末端以 0.2 m/s 运动时，8/32/49/83/191 ms 对应约 1.6/6.4/9.8/16.6/38.2 mm 的位移。该计算只是速度×时间差，不是本机位置误差实测。高速运动影响更大。
- 对低速、厘米级容差抓取，缓存对齐后的结果具备试采条件，应在真实任务样本中验收成功率；不能仅凭静止复测宣布训练质量合格。
- 对插接、快速双臂配合、碰撞/触觉接触学习，30–50 ms 跨相机差和源时钟几毫秒偏差仍可能关键，需要更紧时间基准、硬件/曝光同步或独立物理同步验证。
- 关节可在短且连续的时间段按统一时钟插值；腕力冲击不宜简单线性插值抹平，保留高频原始数据并选用窗口聚合/峰值等任务相关处理。
- 离线训练可以等待所需帧到齐后再对齐；实时策略则不能使用尚未到达的未来观测，必须单独评估端到端观测年龄。

按本窗口估计，3 RGB 最近匹配帧在锚点后约 105 ms 内可取到，包含环视约 226 ms。可以把约 250 ms 等待与更长的有界缓存作为起始试验参数，但正式逻辑应依据各路数据水位与超时，遇到缺帧标记/拒收；这不是已验收的最坏时延上界。

## 部署建议

推荐数据流：

G1 SDK / 遥操接收端 → G1 有界采集缓存 → G1 本地原始 episode 文件 → 有线分片/按 episode 同步 → PC 校验与时间对齐 → LeRobot 转换 → 训练。

1. G1 负责轻量采集和可靠落盘，保存 SDK 提供的 JPEG 原始字节、uint16 深度、关节/夹爪/六维腕力、动作序号与源时间戳。不必在 G1 实时安装/运行完整 LeRobot 编码流水线。
2. 保留源时间戳、G1 接收单调时间、原始数据有效性/序号以及动作创建/接收/下发时间。不要用同一读取时间覆盖所有模态源时间。
3. 每个 episode 或分片完成后通过 192.168.1.88 的有线连接上传，PC 校验大小与哈希，G1 保留原件直到成功确认。无需等整天采集结束才上传。
4. PC 进行源时间基准检查、配对与质量筛选，随后创建固定 fps 的 LeRobot 行时间。原始非均匀时间戳和每模态配对误差另存字段，避免以重编号掩盖采样缺口。
5. 如果采集仅需 3 路 RGB、关节及腕力，使用“G1 薄采集/缓冲转发＋PC 经有线落盘”也合理，网络带宽上已具备条件；应有 G1 端短期缓存、序号及断线补传。PC 仍应接收源时间戳，不能按包到达时刻配对。
6. 如果希望完全由 PC 直接订阅 SDK/DDS，还需核实发现机制、网卡选择和数据通路确实绑定有线。此次 SSH 带宽测试未验证该具体方案，不能将其标为已通过。

正式验收建议：稳定校时后，以真实采集组合和遥操负载连续录制至少 30 分钟，统计独立帧数、缺帧、配对误差尾部、队列峰值、磁盘持久化延迟、断线补传与 episode 完整性。达到任务设定阈值再开始批量录制。本轮未执行这项长期测试，也未改动现有采集程序。
