## 目标和边界

本轮范围已由用户明确：CPU 在线验证、同帧迁移一致性、运算时间对比和现场
新采集重复性。GPU 优化确定放到下一轮，本轮不实现 GPU 后端或构建 GPU 新镜像。

利用当前现场姿态，验证新鲜采集数据能够经过现有感知前端和人工确认，
交给固定 `_03` 计算镜像，获得可追溯的 base_link 箱体中心、姿态或明确拒绝。
用同帧旧环境 V5 对照验证容器迁移一致性，用独立新采集验证现场重复性。

流程：宿主机 SDK 采集 → 宿主机现有 SAM3/LingBot 客户端与 ROI → 人工确认
→ 冻结 Observation → 断网 `_03` 内 V5 → 独立结果目录。
SAM3/LingBot 模型仍在远端。当前镜像入口不含完整在线前端；这次结论只能称
“在线采集接入 Docker 计算”，不能称“全部感知步骤已迁入 Docker”。

固定镜像：`s1-box-pose-compute:v5_2_v5_3b_20260911_03`。
执行前核验记录 Image ID：
`sha256:651bcf7087b9ba1ee2702a4b58ef488936c45251e2a661db8b41d547042bae89`。
不更换算法、参数、模型或门限。新增离线异常用例仍按
[离线计划](s1_orin_compute_offline_test_plan_20260912.md)保留为待完成事项。

## 工程实施细节

现有 `run_pose_once.py` 在确认后也会运行宿主机 V5；执行前核对部署代码。
优先复用这条可用入口，把宿主机 V5 结果作为同帧对照，再导出本次 bundle
送入 `_03`。因此可能会有一次宿主机 V5 和一次容器 V5，报告分别计时。
若现有现场输出不能直接导出，先补齐本地转换并验证输入一致性，不临时改写
旧发布包或用别的历史案例充当本轮在线结果。

串行执行，容器沿用 6 CPU/8 GiB/256 PIDs、非 root、只读根与输入、断网，
每次使用专属输出父目录。服务超时/401、输入同步失败、确认哈希不匹配或
容器异常立即终止该次，不自动沿用旧 mask、深度或位姿；修复后使用新 run ID。
不故意向在线服务注入错误；异常注入仍在离线 fixture 中完成。

报告拆分采集、SAM3/LingBot/ROI、人工等待、导出、容器启动及 V5 计算时间。
记录 CPU、容器内存周期采样和 OOM 状态；不把采样峰值称精确历史峰值。
重复性仅统计 accepted 正式位姿，拒绝诊断单列；yaw 按箱体 180° 对称处理。
少于两次 accepted 不报告重复性标准差为有效结论；五次也只是小样本描述。
未确定应用精度需求，本轮不临时设置毫米级物理精度合格线。

## 本轮必选：计时对比

计时对比纳入本轮必选。用户已明确 GPU 方案移至下一轮；本轮建立 CPU 基准。

每个 run 记录以下时间（秒，单调时钟测量区间）：采集、SAM3 请求、LingBot
请求、ROI、人工确认等待、bundle 导出、容器启动/入口准备、V5 后端计算、
结果写入，以及外部完整命令墙钟耗时。已有入口只能给出合并耗时时保留合并值，
分项标为未测，不通过不同计时边界的差值冒充纯启动耗时。若服务并行，注明
重叠，不能直接把各请求时长相加当端到端时长。

输出两类端到端时间：含人工等待的现场总时间，以及扣除已测人工等待的
机器处理时间。旧 V5 对照运行额外消耗的时间单列，不算容器生产路径必需成本。
现有入口若先计算宿主机 V5，再导出给容器，完整实验总时长和组合阶段得到的
容器路径时长分别标注，后者不是独立执行整条容器路径的实测墙钟时间。

同一新采集帧配对比较：

| 指标 | 宿主机旧 V5 CPU | `_03` V5 CPU |
|---|---|---|
| 同输入后端计算时间 | 实测 | 实测 |
| 完整计算命令墙钟时间 | 同等计算边界下实测；无法分离则标未测 | 实测（含容器开销） |
| accepted/rejected/error | 记录 | 记录 |
| 中心/矩阵差异 | 基准 | 按迁移容差验收 |
| 内存与资源 | 记录可取得指标 | 采样、限额、OOM |

记录耗时差及比值 `T_host / T_container`，大于 1 表示此项容器更快，小于 1
表示更慢，不能预先承诺容器提速。控制/记录线程数、CPU 限额、后台负载、
首次运行与后续运行、可读取的温度/频率状态，不更改机器人功耗模式或锁频。
无法统一条件时标为“当前部署运行对比”，不能把全部差异归因 Docker。
左右腕、accepted/rejected 分组；5 次报告逐次值、中位数、均值、最小/最大，
不使用少量样本宣称稳定 p95。历史右腕约 14.7–14.9 秒、左腕约 40.4–52.6 秒
仅作不同冻结案例的参考，不与本次不同场景直接计算加速比。

## 下一轮：GPU 优化（本轮不执行）

GPU 评估结论（本地源码证据）：当前 `v5_2_visibility.py` 和 `mesh_shell_fit.py`
使用 NumPy、SciPy `cKDTree` 与 `least_squares`，现有路径没有可直接启用的 GPU
开关。镜像已通过 CUDA 核函数测试，表示硬件访问可用；启用 NVIDIA runtime
不会自动将这些 CPU 计算迁移到 GPU。SAM3/LingBot 的远端模型耗时也不会因
Orin 容器启用 GPU 而自动下降。

GPU 已确定移至下一轮，届时按以下顺序实施：

1. 在本轮保存的冻结数据上做独立 CPU profiling，确定多初值、可见性、最近邻、
   残差和优化迭代的实际占比。profiling 有开销，其时间不作为正式基准。
2. 根据热点选择最小 GPU 原型，例如点变换/可见性或分块最近邻/残差批量计算。
   这些只是候选，尚不能认定是瓶颈；避免全量点对距离矩阵造成内存增长。
3. 核验 Orin/JetPack/CUDA 与所选 GPU 库的兼容性，使用独立新镜像。保留 `_03`
   作为 CPU 基准，不在宿主机安装新算法依赖，不覆盖 `_03` 标签。
4. 若保留 CPU 优化器，测清 CPU/GPU 数据往返和同步开销；若更换求解器，按
   算法变更进行完整回归，不能当纯环境迁移。先保持数值精度和目标函数语义。
5. 同输入 CPU/GPU A/B：分别记录首次初始化、预热后计算、传输及完整后端耗时；
   GPU 异步操作需同步后停止计时。状态、拒绝原因及位姿满足预先确定的容差，
   并且完整后端耗时有收益，才考虑接入在线入口。

本轮不承诺 GPU 加速比、不为等待新镜像耽误当前观测位测试。计时工具如需
补充，可在外部包装 `_03` 测量；不要修改镜像内算法后继续声称测试原 `_03`。

## FDP 对照与最终验收

“FDP 位”仅表示现场观测姿态，本轮必选对照为同帧旧 V5，便于隔离环境差异。
可在主链路通过后追加同帧 FDP：固定同一目标、RGB、mask、K、TF 和模型，
记录深度编码量化差异，比较中心距离、对称 yaw 与投影。FDP 不是独立真值，
不得将后端差异命名为绝对定位误差。该附加请求在执行前明确纳入当次范围。

最小成功：右腕一组新鲜数据完成感知、人工确认、容器计算和同帧旧 V5 对照，
没有工程错误；accepted 表示定位候选通过算法门禁，rejected 表示链路跑通但
本帧没有可用正式位姿。error 不算通过。随后完成左腕覆盖与现场重复性报告。
`accuracy_validated=false`、`grasp_ready=false` 保持不变；V5 仍为 xyz/yaw，
roll/pitch 是直立先验，不因到达 FDP 位就认定箱体直立或适用于倾斜箱体。

本测试只读腕部相机和 TF/状态，无设备预期运动，机械臂、夹爪、升降和底盘
均不受本测试控制，故无测试主动运动速度。现场保持静止、工作区净空和急停
可用；其他任务运动会造成碰撞风险与输入失效，应先停止本次采集测试。
若需改变姿态，另列具体设备、目标、速度、碰撞风险及急停要求，并取得新的
逐步运动确认。制定本方案不代表已获执行 SSH 或运动的授权。

依据：现有 Docker 执行记录、实时感知实现记录、双腕同帧 V5/FDP 对照记录。
