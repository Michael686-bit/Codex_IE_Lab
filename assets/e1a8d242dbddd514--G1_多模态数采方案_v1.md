# G1 多模态数采方案 v1

日期：2026-09-20。状态：方案草案；本次仅制定计划，没有启动正式采集、修改控制器或部署新服务。

## 1. 明确目标

建立一套可重复、可追溯、能够断点传输的 G1 多模态演示采集流程，同时交付：

1. **完整原始数据包**：保存用户指定的全部图像、深度、腕力、关节与夹爪数据，以及源时间戳、标定和有效性信息。保留原生频率，不因训练帧率降低而丢弃原始数据。
2. **可训练的 LeRobot 0.4.4 数据集**：在 PC 上完成时间映射、对齐、质量过滤和转换；保留任务文本、实际动作和 episode 边界，验证训练读取。
3. **逐 episode 质量报告**：明确缺帧、时间偏差、数据无效、指令执行失败及任务成功/失败，不以“文件生成成功”替代数采验收。

第一阶段目标是“全部通道可靠采全、动作可追溯、数据集可回读”，不是立即完成大规模训练或证明精密力控性能。先做 10 个有明确任务的试采 episode，再根据任务成功率、动作覆盖与质量决定正式数据规模；正式任务类别和总 episode 数尚未确定，不凭空设定数量。

## 2. 固定采集范围

| 类别 | 通道 | 保存内容 | 原始速率目标/当前观测 |
|---|---|---|---|
| 头部 | 左目、右目 RGB | 1280×960，SDK 原始 JPEG、内参、畸变、时间戳 | 各约 15 FPS |
| 左腕 | RGB、深度 | RGB 1280×720；深度 uint16 1280×720、depth_scale | 各约 15 FPS |
| 右腕 | RGB、深度 | 同左腕 | 各约 15 FPS |
| 前方环视 | 左前、右前 RGB | 1280×960，原始 JPEG、标定信息 | 各约 10 FPS |
| 腕力 | 左腕、右腕 | Fx/Fy/Fz、Tx/Ty/Tz；单位 N、N·m；坐标系和补偿状态 | 各约 120 Hz，实测约 119 Hz |
| 双臂 | 左臂 7 关节、右臂 7 关节 | 名称、位置、速度，以及 SDK 实际提供的 effort/current 等字段 | 约 60 Hz |
| 其他关节组 | head、leg、chassis | 按 SDK 实际枚举完整记录，单位按关节类型核实 | 约 60 Hz |
| 夹爪 | 左夹爪、右夹爪 | 开度、速度、effort、运动标志、反馈时间戳 | 各约 120 Hz |

合计 **6 路 RGB＋2 路深度**；不采左右后方环视。本轮机器人快照显示身体关节为 25 个，正式启动时重新读取关节名称和顺序，禁止假设所有机型均为同一长度。双臂角度以 rad 表示；其他关节依据 URDF/SDK 核实旋转、平移等单位，不统一强写 rad。

所有列出的通道属于必采范围；某通道缺失时预检失败，或明确把该 episode 标记为不完整，不静默降级。

原始反馈保留不等于认可其物理含义：现有双臂 effort 为 0、夹爪 effort=100，不能当成已校准的力；六维腕力保留原值并注明是否归零/重力补偿。未知字段含义用有效性/语义状态标记。

## 3. 是否使用指定镜像

**使用 `vla-g1-teleop:lerobot-0.4.4` 作为 PC 端基线。G1 端不直接运行这个镜像。**

- 已通过本机 Docker 元数据确认镜像存在，架构 linux/amd64，镜像 ID 为 `sha256:fe3f46c4d664f8cb45b428274a4cbc6945aa498b2681e3b724a056baec107922`。
- 项目 Dockerfile 固定 LeRobot 0.4.4；现有脚本使用 host 网络并可挂载 GP001 与 x86_64 Galbot SDK。SDK 是运行时挂载内容，不能认为只固定镜像就固定了完整运行环境。
- PC 镜像负责遥操输入/会话管理、接收与校验、离线转换、质量检查及训练数据读取验证。实际训练环境另行确认所选策略与算力兼容性。
- G1 使用已验证的 aarch64 SDK 与系统 Python，运行轻量原始记录器；避免在实时采集期间解码、缩放和重新编码全部视频。
- 如后续要把 G1 记录器容器化，应独立构建并验收 ARM 镜像，不把当前 amd64 镜像直接搬到 G1。
- 每次采集保存镜像 ID、源码版本或哈希、挂载 SDK 版本、机器人固件、URDF/标定哈希及运行参数。镜像 tag 不是不可变版本标识。

9 月 18 日的 20 帧 LeRobot 回读测试是在 PC 项目虚拟环境中完成，不能替代当前镜像中的验收。本计划包含镜像内复测。

## 4. 部署与数据流

```text
PC：GP001 / 操作员 / 会话管理
          │ 指令、序号、PC 创建时间
          ▼ 现有已验证控制通路
G1：传感器订阅＋控制事件记录
          │ 原始源时间戳＋接收时间＋动作事件
          ▼
G1：独立有界队列 → 原始 episode / 分片可靠落盘
          │ 已完成分片，经现有千兆有线异步传输
          ▼
PC：大小/哈希校验 → 归档 → 时钟映射与对齐 → LeRobot 导出 → 质量报告
```

网络明确使用 PC `192.168.1.99` 与 G1 `192.168.1.88`。`10.34.216.136` 为无线访问路径，不作为正式全量原始数据唯一通路。

G1 本地落盘优先于上传；每段文件关闭并确认完成后传输，不直接同步仍在追加的文件。PC 校验完成才确认接收，G1 原件按显式保留策略处理，首轮验收不自动删除。网络断开不让采集线程阻塞；存储/队列不可恢复故障应使 episode 明确失败并通知会话管理，控制安全逻辑独立处理，不受写盘阻塞。

PC 只读转换任务应使用独立启动入口，避免当前 `docker/run.sh` 必须存在 GP001 串口才能运行的问题。此为计划内改造，本次不修改脚本。

## 5. 时间基准与采样策略

### 原始层

- 原生频率保存每个独立样本，检测 SDK 重复时间戳，不把重复轮询当成新帧。
- 每条记录保存 `source_timestamp_ns`、时钟域标识、G1 `receive_monotonic_ns` 和 `receive_wall_ns`、会话/通道/序号、有效性标记。源时钟含义未知时明确标记 unknown。
- 保存 wall↔monotonic 与 PC↔G1 的映射测量、残差及分段信息。时钟发生跳变时分段，不使用单一常数硬套整个 episode。
- 当前 `teleoperation/run_arm7_record.sh` 固定传入 `--g1-clock-offset-ms 104`，与本次实测动态偏差不匹配；正式数采前必须移除这类固定历史补偿，换成经过验证的动态映射，且不得破坏控制器已有新鲜度检查。
- 机器人时间戳曾领先本地读取时刻约 7–11 ms，需排查控制器/相机源时钟和时间戳语义。即使最近邻差小，也不能据此声称物理同步已达毫秒级。

### 导出层

- v1 默认统一 **10 Hz** 导出，以匹配两路前环视约 10 FPS；头部/腕部原始 15 FPS、低维高频原始数据全部保留，后续可按策略另导出 15 Hz 子集。
- 使用明确的 10 Hz 网格和统一时间域配对，记录每路实际选中帧的源时间与偏差。此前以左腕图像为锚点的统计只作基线，必须重新验证固定网格导出的整体误差。
- 缓存等待各路观测到齐。重复帧、缺帧、超限时间差必须可追溯，不能用“统一填相同 timestamp”伪造同步。
- 关节/开度可在连续短间隔内插值；发生大缺口拒绝插值。腕力保留原始高频数据，默认近邻取样并保留窗口信息；接触峰值处理按后续任务单独设计，避免插值抹平冲击。
- 训练行的 LeRobot `timestamp` 与固定 fps 一致，原始采集时间戳、所选帧索引和误差作为独立信息保存。

低速操作试采的初始工程指标：统一网格配对的绝对偏差 P95，15 FPS 相机 ≤35 ms，10 FPS 环视 ≤55 ms，关节 ≤10 ms，腕力/夹爪 ≤6 ms；单条超限候选门槛分别为 50/100/20/20 ms。它们是待试验验证的低速数采标准，不是 LeRobot 官方要求，也不是精密接触任务标准。模型所需任一模态超限，该训练样本/片段不准静默入库；原始数据仍保留。

时钟准备目标：在低 RTT 的有线测量下，PC↔G1 偏差及变化进入预定范围；优先达到 |offset|≤2 ms、连续 60 秒无时钟跳变。达不到时必须验证分段时钟映射的残差，而非放宽或忽略时间检查。控制器/相机源时钟另行核实，PC/G1 主机校时通过不自动代表所有设备校时通过。

## 6. 动作与训练字段

用户列出的传感器覆盖 observation；要用于模仿学习，还必须记录实际动作。

- 原始动作事件保存：GP001 原始输入、映射后目标、限位/限速后的实际下发值、command_id、PC 创建/发送时刻、机器人端能够实际观测到的接收/下发/接受状态，以及失败/拒绝/急停事件。
- SDK 返回成功不自动等于硬件已执行；若机器人端执行/接受时间无法取得，必须标记未知，不能用 RPC 返回时刻冒充。
- v1 优先沿用已有经过验证的控制路径，不因“记录双臂状态”就要求同时改成双臂控制。现有 arm7 记录入口主要围绕左臂，不能声明它已经完成双臂与左右夹爪全控制验收。
- action 的维度由实际受控通道决定，固定在对应数据集 schema 中。左臂 7 关节＋左夹爪可以形成独立 8 维动作版本；只有双臂和两夹爪控制均通过验证时，才导出对应 16 维动作版本。具体入口是否含夹爪还需阶段 1 核实。不能拿观测位置充当未下发的动作，也不将不同动作 schema 混为同一数据集。
- 双臂、头、腿、底盘与左右夹爪反馈无论哪些组受控，都按本方案完整记录。被动/未受控组作为 observation。

建议导出内容：

| 字段组 | 内容 |
|---|---|
| `observation.images.*` | head_left、head_right、left_wrist、right_wrist、front_left、front_right，共 6 路 RGB 视频 |
| 低维 observation | 双臂及所有关节组的位置/速度；双夹爪状态，固定名称、顺序和单位 |
| 腕力 | 左右各 6 维，原始值与补偿状态；策略是否实际使用由训练输入配置决定 |
| 深度 | 左右 uint16 原始深度、scale、内参、帧索引和源时间戳 |
| `action` | 对应版本实际受控通道的下发目标，不是反馈值 |
| episode/task | 任务描述、开始/结束、成功/失败、失败原因、操作者/session 与环境标识 |
| 时间/QC | 源时间、时钟映射、对齐误差、缺帧/重复/有效性与动作关联 |

**深度专项边界：** 之前只验证了深度读取，尚未验证本地 LeRobot 0.4.4 对 uint16 深度的完整存取。原始包必须无损保存 uint16＋scale；优先作为数据集随附的无损深度文件与索引，由明确的适配器读取。是否使用标准 feature 或附加资源，以镜像内验证结果确定，不假定 RGB 视频通路自动支持深度。只有两个深度通道逐像素无损回读、并能通过目标数据加载接口取出后，才宣称“全部指定模态可用于训练”。不能以 8-bit 深度预览代替原始深度。

## 7. 容量预算

按 9 月 20 日实测字节率，移除两路后环视后，本方案约 **70.27 MB/s、253 GB/小时、126 GB/30 分钟**。其中双路未压缩深度约占 55 MB/s；图像内容与压缩设置会改变实际大小。

- 30 分钟连续原始录制，建议 G1 至少预留 200 GB；PC 若同时保留原始副本、转换产物及临时文件，预留至少 300 GB，仍需按实测转换峰值修正。
- v1 保存原始 JPEG 字节与无损深度，先验证可靠性，再评估无损深度压缩；不预先承诺压缩比。
- 现有千兆有线短测约 113.7 MB/s，满足平均传输的初步条件，但未验证全流程写盘与长期竞争负载。
- 制定容量低水位、队列溢出、写盘错误与不完整 episode 的处理规则，禁止静默丢弃必采通道。

## 8. 实施阶段与验收

| 阶段 | 工作与产物 | 通过条件 |
|---|---|---|
| P0：冻结环境与 schema | PC 镜像内核实 LeRobot/SDK/编码器，明确源时钟、通道、单位和 action；生成 manifest | 全部必采通道和动作语义明确，版本可追溯，时钟问题有处理方案 |
| P1：原始记录器 | G1 订阅、去重、有界队列、分片落盘；PC 会话与动作事件接入；先静态录制 | 全通道数据齐全；磁盘数据和统计可回读；SDK 原始深度保持 uint16；异常显式报告 |
| P2：传输与转换 | 有线断点传输、校验；10 Hz 时间对齐；镜像内 LeRobot 转换和深度适配 | 六路 RGB 均能逐帧解码；深度逐像素一致；低维和原始时间戳回读一致；动作对应关系可追溯 |
| P3：持续可靠性 | 30 分钟全部指定通道录制；静态断网/恢复、写盘失败等故障验证；安全条件满足后加真实遥操负载复测 | 无未解释丢数；所有缺口有记录；队列有界；控制线程不被记录阻塞；文件校验通过；配对指标达到试采门槛 |
| P4：任务试采 | 选择一个代表性低速任务，采 10 个完整 episode，包含明确成功/失败标注 | 每段通过完整性检查；可视回放图像/状态/动作一致；训练 dataloader 能读取所需全部模态 |
| P5：批量采集 | 固定通过验收的版本和参数，按任务定义数量与覆盖范围 | 持续自动 QC；每天抽查；失败数据隔离；变更版本后重新验收 |

阶段顺序：P0 → P1 → P2 → P3 → P4 → P5。先验收完整记录能力，再进行任务试采；本计划不直接启动运动测试。

尚需在任务试采前明确：具体任务、实际控制哪一侧/哪些关节、是否同时控制两个夹爪、单段时长与成功判据。采集范围按用户本次指定固定，不因这些任务选择而缩减传感器覆盖。

## 9. 最终交付与完成定义

交付可复现的 G1 原始记录器、PC 镜像运行入口、原始 schema/manifest、可靠传输工具、LeRobot 转换器及深度加载适配器、episode 质量报告、30 分钟持续测试报告和 10 个任务试采 episode。

只有“全部指定传感器采全＋动作真实可追溯＋时钟问题受控＋落盘和传输可恢复＋镜像内完整回读通过＋任务试采验收”全部满足，才将方案标记为正式数采就绪。单纯保存视频、只生成没有 action 的数据集，或仅通过静止格式测试，均不算完成。

依据：项目 Dockerfile、compose.yaml、docker/run.sh；本机镜像 inspect；`reports/sensor_audit_20260918/` 和 `reports/timestamp_audit_20260920/` 实测报告。
