## 最适合你先做的事情

优先级从高到低：

1. **历史运行分析工具**

   自动读取一次 run 的 `RESULT.txt`、配置、感知结果、抓取目标、IMC 轨迹和日志，输出：

   - 哪些阶段完成；
   - 失败发生在哪一层；
   - 使用了哪份感知结果；
   - 是否真正执行抓取、导航、放置；
   - 源码、配置和运行结果能否对应。

   这是纯离线工作，不影响同事调机，而且很快能让你理解全系统。

2. **双臂抓取目标可视化**

   将箱体、左右 TCP、预抓位姿、内收方向、抬升方向画出来，重点发现：

   - 左右手写反；
   - 毫米与米混用；
   - 坐标轴方向错误；
   - 箱体尺寸或 mesh 尺度错误；
   - 目标间距不合理。

3. **IMC 轨迹检查器**

   针对历史轨迹绘制每个关节随时间的变化，检查：

   - 首点是否连接当前姿态；
   - 是否超限；
   - 相邻点是否跳变；
   - 终点误差；
   - TCP 接近方向；
   - 是否真正启用了碰撞检查。

4. **`put/down` 离线设计**

   这是当前主要缺口，但不要从真机下降试起。可以先完成：

   - 卸货平台测量表；
   - 箱底—TCP—夹爪接触面的几何关系；
   - 预放、下降、开爪、撤臂状态机；
   - 各阶段的停止门和失败恢复矩阵；
   - 历史数据上的目标生成及无执行规划。

## 要不要改调 G1？

**如果只是为了练手，我不建议立刻转 G1。**

原因是：

- 换机器人会额外引入型号、SDK、控制器、末端工具、关节定义和安全边界差异；
- G1 上“会动了”不代表能直接解决 S1 拆垛问题；
- 你可能同时面对两套都没完全理解的系统；
- 实机练手依然有碰撞和状态破坏风险。

但以下情况适合用 G1：

- S1 长期被同事占用，你无法获得任何只读或规划机会；
- G1 有独立、安全的仿真或教学环境；
- 两者确认使用相同或高度相近的软件接口；
- 你在 G1 上练的是可迁移能力，例如状态读取、坐标变换、离线 FK/IK、轨迹审查，而不是记住某组关节数值；
- 团队确实希望形成 G1→S1 的迁移路线。

在确认 G1 的确切型号、SDK版本、机械臂配置和末端执行器之前，这些兼容性都应标为**待验证**。不要假定银河通用的两台机器人接口和安全姿态天然一致。

## 12. 用户

走读一次历史 run 是什么意思？

## 13. 助手

“走读一次历史 run”，就是选一次以前真实执行产生的运行记录，**不重新控制机器人**，像复盘事故录像一样，从头到尾追踪这次任务发生了什么。

这里的 `run` 指一次拆垛任务留下的完整运行目录，通常包含：

```text
运行配置
→ 相机 RGB/深度图
→ SAM3 mask
→ ROI/H4 目标选择
→ FoundationPose++ 位姿
→ 左右臂抓取目标
→ IMC 规划轨迹
→ SDK执行日志
→ RESULT.txt
```

## 具体怎么走读

建议先从 `RESULT.txt` 倒着看。

### 1. 看最终结果

先回答：

- 任务最终成功还是失败？
- 箱子最后在哪里？
- 执行到了哪个阶段？
- 是否真的执行了抓取、导航、放置？
- 有没有明确的失败原因？

例如之前看到的一次记录中：

```text
箱子已运到卸货位置
仍被双臂夹持
put_executed=false
```

这说明运输到位不等于整个拆垛成功，放置阶段实际没有执行。

### 2. 恢复时间线

按日志时间整理：

```text
14:00 采集 RGB-D
14:01 SAM3 生成 mask
14:02 FoundationPose++ 返回箱体位姿
14:03 生成双臂目标
14:04 IMC 规划成功
14:05 双臂接近
14:06 合爪
14:07 抬升
14:08 底盘导航
14:10 流程停止
```

时间线能揭示程序说的“成功”到底对应哪个阶段。

### 3. 查看感知输入和输出

检查：

- RGB 图里选中的是不是正确箱子；
- mask 是否覆盖完整；
- 深度是否存在空洞或异常；
- H4 是否选对层；
- FoundationPose++ 的箱体坐标轴和尺度是否合理；
- 使用的是本次新鲜感知，还是旧缓存结果。

### 4. 追踪坐标变换

把关键关系写出来：

```text
相机中的箱体位姿
→ 变换到 base_link
→ 加上箱体到左右抓取面的偏移
→ 得到左右 TCP 目标
```

重点检查：

- 单位是米还是毫米；
-矩阵乘法顺序；
- 左右臂是否写反；
- TCP 朝向和接近方向是否正确；
- 是否混用了不同时间的机器人状态和相机图像。

### 5. 查看规划与执行

规划成功只代表“算出了一条路径”。还要继续核对：

- 首点是否接近机器人当时姿态；
- 关节有没有超限或突然跳变；
- 是否做了碰撞检查；
- 轨迹是否真正下发；
- SDK 是否返回成功；
- 下发后机器人是否到达目标；
- 抓到箱子后是否有接触或负载证据。

### 6. 写一页复盘结论

最终最好形成这样的表：

| 阶段 | 输入 | 输出 | 是否成功 | 证据 | 问题 |
|---|---|---|---|---|---|
| RGB-D | 腕部相机 | 彩色和深度图 | 是 | 文件存在 | 时间是否同步待查 |
| SAM3 | RGB | mask | 是 | mask 图片 | 边缘缺一小块 |
| 位姿估计 | RGB-D、mask | 6D 位姿 | 是 | JSON | 精度待验证 |
| 双臂规划 | TCP 目标 | 轨迹 | 是 | plan 文件 | 碰撞检查关闭 |
| 抓取 | 轨迹 | 箱体抬升 | 有历史证据 | 日志/图像 | 力反馈未标定 |
| 放置 | 卸货目标 | 无 | 否 | `put_executed=false` | 当前主要缺口 |

走读的目的并不是证明这次 run “成功了”，而是让你能够准确回答：

> 这次任务用了什么输入，经过哪些程序和坐标系，在哪一步得到了什么结果，最终停在哪里，以及结论有什么证据。

这通常是新加入项目最快的入门方法：不用冒真机风险，却可以同时熟悉感知、规划、控制和工程目录。
