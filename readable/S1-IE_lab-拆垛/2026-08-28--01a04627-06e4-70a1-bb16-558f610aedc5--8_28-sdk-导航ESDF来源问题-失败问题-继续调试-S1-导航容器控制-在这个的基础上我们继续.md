## 10. 助手

这个新现象的核心是：SDK 通信成功，但导航系统当前没有给出有效的地图定位。因此不是“容器控制失效”，而是“定位尚未建立或定位丢失”。

几个字段要分开理解：

- `localized: false`：当前不能信任 `map` 坐标系位姿，这是需要解决的主问题。
- `current_pose_map: null`：CLI 主动避免在未定位时读取/输出无效地图位姿，行为正确。
- `navigation_status: UNKNOWN`：没有有效导航任务时可能出现，不等同于故障。
- `bounding_boxes: []`：没有登记携带物过滤框，与定位失败基本无关。
- `ok: true`：这里只表示 SDK 初始化和查询成功，不表示“已经具备导航条件”。这个字段表达得不够清楚，后续应改成 `query_ok=true`、`navigation_ready=false`。

我认为最可能有三类原因，按优先级排列：

1. 初始化后的状态同步延迟
   当前 `pose` 命令在 `navigation.init()` 后立即读取一次。SDK 初始化成功不一定意味着定位状态已经同步到客户端。以前可达性 RPC 也出现过需要预热的现象。

2. 定位服务当前尚未收敛或已经丢失
   例如机器人刚启动、雷达数据异常、定位置信度不足、地图服务尚未加载完成，或者机器人被人工移动到了与地图不一致的位置。

3. 地图或底层服务发生变化
   需要确认当前 `/var/maps/cur` 是否仍指向 `room0804`，以及 `localization_server`、雷达采集、机器人状态发布等服务是否正常。

我的排查顺序会是：

1. 改进 `pose` 为纯只读连续观测
   在同一个 SDK 进程里观察约 10 秒，每秒记录：

   - `is_localized()`
   - 当前导航状态
   - 一旦定位变为 true，再读取地图位姿
   - 状态首次变为 true 的耗时

   这一步不会切换控制器、不会重定位，也不会运动。

2. 如果几秒后自动变为 true
   基本可以判断为 SDK/定位状态订阅的启动同步问题。CLI 应加入有界等待，例如最多等待 10 秒，而不是初始化后立即下结论。

3. 如果持续为 false
   再做宿主机只读检查：

   - 定位服务进程是否存在；
   - 当前地图软链接和地图文件是否正常；
   - localization 日志中的 score、地图加载和传感器错误；
   - LiDAR 服务是否运行；
   - odometry 是否可读；
   - 是否存在 TF、时间戳或传感器超时。

4. 暂时不要调用 `relocalize()`
   重定位虽然不会直接驱动底盘，但会改变导航坐标状态。不能随便使用 `[0,0,0]` 或昨天的位姿作为初始值。只有现场确认机器人在地图中的真实位置后，才能设计重定位步骤。

5. 在恢复 `localized=true` 前禁止导航
   当前 CLI 的 `navigate` 和 `relative` 都已经在提交运动前检查定位状态，因此会安全拒绝，不会因为这次输出而误启动底盘。

下一步最合适的是增加一个 `diagnose-localization` 只读子命令，连续采样 10 秒。它能先回答最关键的问题：这是短暂的初始化延迟，还是持续性的定位丢失。当前阶段不需要也不应该尝试底盘运动。

## 两个函数的作用对照

| API | 影响 fusion/nvblox | 影响 ESDF | 影响 PNS碰撞外形 |
|---|---|---|---|
| `add_bounding_box()` | 是 | 是 | 间接影响 |
| `remove_bounding_box()` | 是 | 是 | 间接影响 |
| `attach_box_to_link()` | 否 | 否 | 是 |
| `detach_box_from_link()` | 否 | 否 | 是 |

### `add_bounding_box()`

当前系统已经确认存在这些 fusion服务：

```text
galbot_fusion_add_box
galbot_fusion_get_box
galbot_fusion_remove_box
```

fusion二进制中也有：

```text
AddBoxInfoServerCallback
RemoveBoxInfoServerCallback
=== BOX FILTER === Add points filter box
```

官方 changelog 的描述是：

> 支持 fusion服务动态抠除搬运箱子对应的点云。

所以它的作用是：

```text
LiDAR看到被搬运箱子
    ↓
点落入动态 bounding box
    ↓
fusion在进入 nvblox前过滤这些点
    ↓
箱子自身的观测点不再成为ESDF障碍
```

它不会告诉规划器“机器人现在变大了”，也不会给箱体增加真实碰撞几何。

它会影响同一个 `EsdfGrid` 的所有消费者：

```text
service_navigation_plan
service_motion_plan
```

需要继续验证的细节是：添加过滤框时，fusion是否立即清除框内已经融合的历史体素，还是只过滤后续新点。当前配置：

```text
clear_blind_before_pub_esdf: false
```

所以不能未经实验就假定旧体素会立刻消失。

### `attach_box_to_link()`

官方 changelog 明确说明：

> 支持导航服务识别搬运箱子与环境之间的碰撞关系。

它不进入 fusion，也不改变 ESDF。作用位置是：

```text
现有EsdfGrid
    ↓
PNS碰撞检查
    ├─ 机器人原生碰撞球
    └─ 新增附着箱体几何
```

箱体位姿相对于 `parent_link_name`，随后会跟随该 link运动。

`ignore_collision_links` 只用于忽略“附着箱体与指定机器人link”之间的预期接触，不会让箱体忽略环境障碍。

另外，`GalbotMotion` 有自己独立的 `attach_target_object()`/`attach_tool()`；不能假定 Navigation的附着箱会自动同步给所有操作规划场景。

## 为什么携箱时两个函数通常都需要

只使用 `attach_box_to_link()`：

```text
箱体真实几何进入PNS
但LiDAR仍看到箱体
→ ESDF又把箱体当外界障碍
→ 可能自碰撞/近障碍报警
```

只使用 `add_bounding_box()`：

```text
LiDAR箱体点被过滤
但PNS不知道机器人携带箱体后变宽/变长
→ 可能规划出底盘能过、箱体过不去的路径
```

组合使用：

```text
add_bounding_box()
→ 清除箱体自观测点

attach_box_to_link()
→ 保留箱体真实碰撞外形
```

这是正确的携箱导航建模思路。
