- 其中当前能看到 `sessions/`、`archived_sessions/`、`session_index.jsonl`、`state_5.sqlite`、`thread_history_1.sqlite`、附件、shell 快照和 writer locks；共检测到 47 个会话 JSONL 文件。
- 这些属于 Codex 内部生成状态，不建议手工修改或加入项目 Git。

对话与项目大致这样关联：

```text
Codex 任务/对话
    ├── 保存自己的 transcript 和任务状态 → ~/.codex/
    ├── 记录关联的工作目录              → .../ChatGPT/S1
    ├── 开始工作时读取项目规则          → S1/AGENTS.md
    ├── 工作过程中读取当前文件          → S1/docs、experiments、源码
    └── 将需要长期保留的结论写入文件    → knowledge_base.md 等
```

官方文档也明确说明：

- 本地项目把聊天连接到电脑上的一个文件夹，但每个聊天仍保留自己的 transcript。
- Codex CLI/桌面端记录聊天的工作目录，同时从当前工作树读取文件。
- 应当把必须跨任务保存的规则和知识放在 `AGENTS.md` 或版本化文档中，而不是只依赖聊天历史。[Projects and chats](https://learn.chatgpt.com/docs/projects)
- `AGENTS.md` 会按照“全局配置 → Git 项目根目录 → 当前子目录”的顺序发现和合并。[AGENTS.md 官方说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

因此，这个仓库当前采取的是一种“双层管理”：

1. Codex 自己保存任务对话和运行状态。
2. S1 仓库保存经过整理、可验证、可版本管理的长期知识。

例如，[README.md](../../assets/576f53f60fbaf225--README.md) 明确说明它连接 Codex 工作与历史 ChatGPT 项目“银河通用s1 项目 代码”；[knowledge_base.md](../../assets/352759744db064d1--knowledge_base.md) 则是二者之间的长期知识桥梁。这种连接主要是通过文档同步实现的，不代表 ChatGPT 项目的所有原始对话自动存放在 S1 目录中。

也就是说：

- 原始对话不是工程事实源；Git 中经过整理的文档才是。

## 高度相似的地方

| 方面 | Codex/ChatGPT 当前机制 | 统一项目协作方案 | 判断 |
|---|---|---|---|
| 项目关联 | 任务通过工作目录关联 S1 | 以项目根目录为协作中心 | 一致 |
| 规则加载 | Codex读取 `AGENTS.md` | 用 `AGENTS.md` 固定协作规则 | 一致 |
| 对话保存 | 每个任务保留独立 transcript | 历史对话作为上下文来源 | 互补 |

| 历史证据 | 对话可以恢复或归档 | 历史对话需标注来源、可信度 | 一致 |
| 任务隔离 | 不同任务各自保留上下文 | 不同实验放入独立目录 | 一致 |

## 一个需要特别修正的旧建议

旧方案曾建议把项目内的 `.codex/` 整体忽略。现在看来应该更谨慎。

必须区分：

- `~/.codex/`：用户级会话、数据库、附件、记忆等内部状态，不应进入 S1 Git。
- `S1/.codex/`：项目级 Codex 配置目录，未来可能包含可共享的环境配置和项目动作，未必应该整体忽略。

当前 `S1/.codex/` 是空的，所以暂时没有冲突。以后若启用项目级 Codex 环境，应按文件类型决定是否版本化，不建议直接写一条 `.codex/` 全目录忽略。
