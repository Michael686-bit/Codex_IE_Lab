## 是否完整覆盖

过滤框相对实体箱的名义余量是：

```text

= [0.10, 0.10, 0.10] m
```

也就是理论上各面只有 10 cm 余量。

但把最新实体箱8个角精确转换到 CLI 过滤框局部坐标后：

```text

[-0.3552, -0.0496] m

过滤框宽度轴范围：
[-0.2500, +0.2500] m
```

因此实体箱一侧超出过滤框约：


## 但这个修改有三个限制

第一，这组参数只匹配最新一次感知和提箱目标，不是所有一键运行的固定姿态。一键流程每次都从 FDP 生成新目标，箱体中心可能改变。

第二，这个中心是“机械臂上抬100 mm后、升降柱继续上升前”的位置。当前一键运输阶段还会把升降柱从约 `0.417 m` 升到 `0.520 m`，箱体相对 `base_link` 的高度随之增加约：

```text
0.520 - 0.417 ≈ 0.103 m
```

因此运输结束时，箱体中心高度近似变为：

```text
z ≈ 0.638697 + 0.103
  ≈ 0.741697 m
```

一个固定在 `base_link` 上的过滤框不能精确跟随这次升降运动。

第三，`add_bounding_box()` 只过滤登记后的新点，不会删除登记前已经融合的箱体体素。更新常量并重新登记，不等于旧 ESDF 箱体痕迹会自动消失。

## 更推荐的修改方式

长期方案应把固定常量改成“默认模板 + 每次运行动态位姿”。

例如：

```python
CARRIED_4317_BOX_TAG = 4317
CARRIED_4317_FILTER_SIZE = [0.60, 0.50, 0.375]
CARRIED_4317_COLLISION_SIZE = [0.40, 0.30, 0.175]
```

然后从本次：

```text
dual_lift_up_100mm_target.json
```

读取：

- 左右 TCP 坐标；
- 箱体 `approach_axis_base_link`；
- 箱体 `object_axes_base_link`；
- 箱体长宽高。

按当前生产公式计算中心：

```python
left_tcp = np.asarray(
    report["targets"]["dual_pre_grasp"]["left"]["tcp"]["translation_m"],
    dtype=np.float64,
)
right_tcp = np.asarray(
    report["targets"]["dual_pre_grasp"]["right"]["tcp"]["translation_m"],
    dtype=np.float64,
)
approach = np.asarray(
    report["mode00_geometry"]["approach_axis_base_link"],
    dtype=np.float64,
)

tcp_midpoint = (left_tcp + right_tcp) / 2.0

# 当前左右接触修正导致中点沿 approach 偏 -5 mm，
# TCP 在箱体中心上方 62.5 mm。
box_center = (
    tcp_midpoint
    + 0.005 * approach
    - np.array([0.0, 0.0, 0.0625])
)
```

方向则来自：

```python
length_axis = report["object_axes_base_link"]["length_x"]
width_axis  = report["object_axes_base_link"]["width_y"]
height_axis = report["object_axes_base_link"]["height_z"]
```

组成旋转矩阵后转换成 `qx,qy,qz,qw`。

这样每次一键运行都能使用自己的 FDP/提箱目标，不依赖某次历史姿态。

## 更稳妥的父坐标系

如果运行时 TF 确认存在并稳定发布：

```text
left_arm_end_effector_mount_link
```

更好的方案是把过滤框表达在该末端坐标系中：

```python
"parent_link_name": "left_arm_end_effector_mount_link"
```

这样升降柱和机械臂带箱移动时，过滤框可随末端 link 更新，而不是固定在 `base_link`。官方示例也允许使用末端 link 作为父坐标系。

- fusion 服务能持续取得该 link 的 TF；
- 左右臂保持刚性抱箱；
- 箱体相对左末端的位姿经过计算和验证；
- TF中断时系统如何处理。

在未验证这些条件前，不能直接把父坐标系从 `base_link` 改成末端 link。

脚本计算：

```python
relative_distance = sqrt(x² + y²)
```

你这里：

```text
x = 3.0
y = 0.0

relative_distance = 3.0 m
max_distance = 5.0 m
```

因为：

```text
3.0 ≤ 5.0
```

所以通过距离保护。如果设置：

```text
--max-distance 1.2
```

脚本会在切换控制器和发送导航命令前直接拒绝。

它不代表：

- 实际路径最多5 m；
- 距离障碍物5 m；
- 导航速度；
- 碰撞安全距离；
- 规划路径长度上限。

## `WAIT_INITIALIZED` 的高概率原因

当前自动链在 `navigation.init()` 后几乎立即执行：

```text
get状态
→ 验证TF
→ add
→ attach
```

PNS attachment客户端尚未完全就绪，所以返回：

```text
(False, "WAIT_INITIALIZED")
```

旧的成功版本存在一个“偶然等待”：

```text
打印参数
→ 等你手工输入确认口令
→ add
→ attach
```

你输入字符的几秒时间，实际给了PNS attachment接口完成初始化的机会。后来删除字符确认后，这个隐含等待也被一起删除，自动链由此暴露出初始化时序竞争。

生产helper也有类似依据：

```python
navigation.init()
time.sleep(1.0)
...
add_bounding_box()
attach_box_to_link()
```

因此这不是箱体参数或左末端坐标系错误，而是attach调用过早。

## 正确修复方式

不建议只盲目加一个固定长延时。更稳健的是：

```text
add并完整回读
  ↓
调用attach
  ├─ SUCCESS：继续
  ├─ WAIT_INITIALIZED：等待0.25秒后重试
  └─ 其他错误：立即失败并回滚
```

建议边界：

```text
最大等待：5秒
重试间隔：0.25秒
最多约20次
```

每次结果都写入：

```json
"attach_box_to_link_attempts": [...]
```

```text

```
