## `COMM_ERR` 的可能原因

按证据强弱排序：

1. 最可能：删除对象本来就不存在
   `before.bounding_boxes=[]` 是直接证据。当前 SDK/服务可能把“删除不存在的 tag”返回为 `COMM_ERR`，而不是幂等地返回 `SUCCESS`。

2. PNS attachment 状态无法通过公开 API 查询
   fusion 中没有 tag，不代表 PNS 中一定没有孤立 attachment。但 `detach_box_from_link()` 同样返回 `COMM_ERR`，所以当前脚本无法确认 PNS 的最终状态。

3. 可能存在初始化时序差异
   旧版等待用户输入，SDK/PNS/fusion 获得了额外初始化时间；当前版会立即发送 RPC。此前当前版的 `attach_box_to_link()` 确实出现过 `WAIT_INITIALIZED`，因此“取消交互等待暴露初始化竞争”是合理怀疑，但本次日志不足以证明它是主因。

不能仅根据字符串 `COMM_ERR` 断言网络断线，因为同一批输出里状态查询正常，随后旧版注册也成功。

## 15. 助手

因为当前两个参数的语义不是“确保已注册”，而是：

> 本次 SDK 会话必须从 tag 不存在开始，完整执行一次 add → 回读 → attach。

当前逻辑相当于：

```python
if tag_4317_exists:
    fail_closed()

add_bounding_box(...)
verify_with_get_bounding_box(...)
attach_box_to_link(...)
```

之所以不自动重新注册，主要有四个原因。

1. `add_bounding_box()` 不是覆盖接口
   tag 4317 已存在时，直接再次 add 很可能返回失败，不能保证自动覆盖旧配置。

2. 重新注册必须先做删除
   真正的“自动重新注册”需要：

```text
detach_box_from_link
→ remove_bounding_box
→ 确认tag消失
→ add_bounding_box
→ 完整回读
→ attach_box_to_link
```

这会主动破坏当前已有状态，不再是简单的注册操作。

3. attachment 无法查询
   SDK 能查询 fusion 过滤框，却不能查询 PNS attachment。因此看到 tag 存在时，只能确认：

```text
fusion过滤框存在
```

不能确认：

```text
PNS碰撞箱仍然附着
```

也不能安全判断应该“复用、重复attach，还是先detach”。

4. 删除接口目前不稳定
   你已经看到：

```text
detach_box_from_link → COMM_ERR
remove_bounding_box  → COMM_ERR
```

在删除语义、服务初始化和不存在对象返回值尚未弄清之前，自动执行“删掉再重建”可能造成：

```text
fusion框被删掉
但PNS attachment没删掉
```

或反过来：

```text
PNS attachment被解除
但fusion框仍存在
```

形成半完成状态。

因此当初选择了最容易证明正确的事务：

```text
起始tag不存在
→ 本会话add成功
→ 本会话回读完全匹配
→ 本会话attach成功
→ 才允许导航
```

所以两个参数目前更准确的名字其实接近：

```text
--create-bounding-box
--create-and-attach-box
```

而不是：

```text
--ensure-payload-registered
```

当前三种情况是：

| 当前状态 | 带两个参数的结果 |
|---|---|
| tag不存在 | 自动 add → verify → attach |
| tag存在且参数匹配 | 仍然拒绝，因为attachment未知 |
| tag存在但参数不匹配 | 拒绝，避免覆盖未知状态 |

理论上可以把它改成真正的“自动重新注册/状态协调”模式，但需要先定义并验证：

```text
已有正确tag时是否允许重复attach
删除不存在tag应算成功还是失败
COMM_ERR具体代表什么
detach/remove是否需要初始化等待与有限重试
删除一半成功时如何恢复
重新注册失败时如何回滚旧状态
```

所以它现在不会自动重新注册，不是忘了调用，而是代码有意避免在已有 tag 上自动执行删除和覆盖。
