## 一句话结论

当前所谓“一键拆垛”，准确说是：

> 对 4317/H4 箱体进行实时感知 → 双臂夹取 → 携箱运输 → 在卸货点高位松爪 → 双臂和底盘返回 SAM 位。

它还不是完整、稳健的“抓取—下降—放置”流程，因为 `put/down` 被禁用，箱子是在抬起高度直接松爪释放的。

## 感知和抓取目标是怎么来的

不是把 FoundationPose 输出直接交给机械臂，而是“实时感知 + 历史人工标定”的混合方案：

1. FoundationPose++ 给出箱体位姿。
2. 把 mesh 坐标轴换成箱体语义长、宽、高轴。
3. 处理箱体绕竖直轴 180° 对称问题。
4. 叠加历史现场修正：
   - 左 TCP：`[-35, -50, 0] mm`
   - 右 TCP：`[-35, +50, 0] mm`
   - 两侧 TCP 姿态最终强制为 `RPY=[0,0,0]`
5. 从预抓位置，两臂沿箱体两侧对向内收 `100 mm`。
6. 合爪后沿 `base_link +Z` 上抬 `100 mm`。

所以它依赖 fresh FDP 定位，但抓取姿态和位置中仍包含 2026-08-06/13 的现场经验参数，不是通用箱体抓取算法。

## 当前最重要的风险

1. 你给出的命令默认是真实运动
   `./run_s1_mode00_one_click.py` 会直接调用：

   ```text
   --execute --unattended
   ```

   即所有人工阶段确认都会被自动跳过。只有显式 `--dry-run` 才不连接 Docker/SDK、不运动。

2. 持箱运输关闭导航碰撞
   当前调用明确传入 `enable_collision_check=false`，而且活跃的一键链路没有调用 `add_bounding_box()` 或 `attach_box_to_link()`。

3. 机械臂碰撞检查不包含现场环境
   IMC 本身以 `check_collision=false` 生成轨迹；之后虽然挂载 GE103 模型逐点检查，但只覆盖机器人本体/自碰，没有把箱体、货垛和现场障碍加入 Motion 场景。

4. 启动持箱保护被人为关闭
   若已有 `s1_sjtu_carried_crate.state`，当前代码只警告并继续新任务，不再拒绝启动。

5. 卸货是高位直接松爪
   没有下降、接触检测和受控放置。

6. GE103 的 `effort=1000` 语义仍未标定。

7. 当前部署目录被 Git 忽略
   整个 `workspace/` 不属于当前 Git HEAD。运行时哈希能发现文件变化，但无法可靠回答“这对应哪个提交”。

## 3. 最核心的方案区别

| 维度 | 现有方案 | 目标方案 |
|---|---|---|
| 系统性质 | 针对固定现场、固定箱型的实验流程 | 可配置、可复现、可验收的拆垛系统 |
| 感知 | 两次独立选择 4317/H4 | 粗选到精定位全过程锁定同一目标 |
| 抓取几何 | fresh FDP 位置叠加历史人工修正 | 实时标定和参数化几何，人工修正有适用范围 |
| 机械臂碰撞 | 主要检查机器人本体和 GE103 自碰 | 同时检查货垛、箱体、平台、周围环境和双臂夹持约束 |
| 携箱导航 | 关闭导航碰撞；未在一键链中注册 payload | 箱体加入 PNS 碰撞模型、从 fusion 自点云中正确过滤，并保持碰撞开启 |
| 放置 | 高位直接松爪 | 预放置、低速下降、接触/高度确认、松爪、撤臂 |
| 异常恢复 | 有停止与部分 run 恢复，但启动时忽略已有持箱标记 | 按“空手、可能持箱、确认持箱、已放置”等状态严格恢复，禁止错误重放 |
| 自动化方式 | 默认 `--execute --unattended` | 默认无运动；真实执行必须显式授权，重要物理阶段保留人工确认 |
| 成功标准 | 程序跑完并返回 SAM | 箱体稳定、准确、安全放置，机器人和软件状态均一致 |
| 版本追溯 | SHA 清单，但部署树未纳入 Git | Git 提交、镜像、配置、模型、现场标定和 run 完整关联 |

最直观地说：

```text
现有方案：
看见箱子 → 抓住 → 运过去 → 在高处松开 → 回来

目标方案：
确认是哪只箱子
→ 在完整碰撞场景中安全抓住
→ 建立携带物模型
→ 碰撞开启地运输

→ 确认箱子已被平台支撑
→ 松爪并安全撤臂
→ 清理携带物状态
→ 验证任务真正完成
```

所以当前最大的缺口不在“能不能把箱子抓起来”，而在三件事：携箱碰撞建模、真正的 `put/down`、以及全过程状态与目标身份闭环。

| 1 | Thor 上的 SAM3 | S1 本机 `YOLO26s-seg` | 目标箱 mask、类别、置信度 |
| 2 | 工作站上的 FoundationPose++ | S1 本机 ICP | 箱体相对相机/`base_link` 的 6D 位姿 |
| 5 | 官方 SDK `navigate_to_goal_v2` | SJTU 原路线的 SFAST-LIO 体系 | 底盘定位、目标跟踪和导航状态 |”


 给我对比“2 fdp++替换成icp且在机器人内运行” 两者的输入和输出分别是什么，现有方案和目标方案的区别是什么？最好有个表格的对比

## 15. 助手

下面只对比第 2 项：

- 当前：工作站上的 FoundationPose++
- 目标：S1 机器人本机运行 ICP

其中目标 ICP 优先接收第 6 项“头部点云与 RGB 融合”产生的目标箱点云；在该链路完成前，也可以先用右腕 RGB-D 生成点云做验证。

## 输入与输出对比

| 项目 | 当前 FoundationPose++ | 目标 S1 本机 ICP |
|---|---|---|
| 运行位置 | 外部工作站服务 | S1 机器人本机 |
| 上游目标类别 | SAM3/ROI 已确定为 4317 | YOLO26s-seg 已确定为 4317 |
| RGB 输入 | 必需，右腕 RGB 图像 | 普通几何 ICP 不必需；彩色 ICP 才使用 RGB |
| 深度/点云输入 | 对齐深度图，当前还经过 LingBot-Depth 补全 | 已分割的箱体三维点云；优先使用头部点云+RGB融合结果 |
| mask 输入 | SAM3 选中箱体的二维 mask | YOLO26s-seg mask，用来从点云中裁出目标箱 |
| 相机内参 | 必需，用于 RGB、深度和 mask 对齐 | RGB-D 生成点云时必需；直接使用已标定点云时可不直接传入 |
| 外参/TF | 捕获时刻的 `base_link <- camera` | 点云来源坐标系到 `base_link` 的时间同步 TF |
| 模型输入 | 4317 的 OBJ mesh | 从同一 CAD/mesh 采样得到的标准箱体模型点云 |
| 初始位姿 | FoundationPose++ 可以从 mask 和模型进行相对鲁棒的初始化 | 必须提供较合理的初值，否则容易落入局部最优 |
| 核心计算 | 学习特征、RGB-D、mask和模型共同估计姿态 | 将模型点云迭代配准到现场目标点云 |
| 主要输出 | `T_camera_from_object` 4×4 位姿 | `T_cloud_frame_from_object` 4×4 配准位姿 |
| `base_link` 输出 | `T_base_object = T_base_camera × T_camera_object` | 若点云已在 `base_link`，可直接输出 `T_base_object` |
| 质量输出 | FDP运行模式、可视化结果、服务状态 | `converged`、fitness、RMSE、内点率、迭代次数、有效点数 |
| 下游接口 | `object_in_camera`、`object_in_world` | 最好继续输出相同字段，减少抓取目标生成模块改动 |

## 两套方案的数据流

### 当前方案

```text
右腕 RGB + 对齐深度
        ↓
LingBot-Depth 补全深度
        ↓
SAM3 mask + 4317 ROI
        ↓
RGB + 深度 + mask + 相机内参 + 4317 mesh
        ↓ 网络传输
工作站 FoundationPose++
        ↓
T_camera_object
        ↓
T_base_camera × T_camera_object
        ↓
T_base_object
        ↓
Mode 00 双臂抓取目标
```

当前 FoundationPose++ 的直接输入可以概括为：

```text
rgb
depth
mask
K
4317 mesh
```

直接输出为：

```text
4×4 T_camera_object
可视化图
FDP运行元数据
```

随后 S1 代码结合捕获时刻相机外参，生成：

```text
4×4 T_base_object
```

### 目标 ICP 方案

```text
头部点云 + RGB
        ↓ 时间同步、标定和投影
YOLO26s-seg mask
        ↓
提取目标箱点云
        ↓
滤波、降采样、法向量估计
        ↓
粗初始化/PCA/OBB/上一帧姿态
        ↓
4317模型点云 ↔ 现场目标点云
        ↓ S1本机ICP
T_base_object + 配准质量
        ↓
Mode 00 双臂抓取目标
```

目标 ICP 的输入应当明确为：

```text
source_cloud：4317标准模型点云
target_cloud：现场分割出的4317箱体点云
initial_transform：ICP初始位姿
point_cloud_frame：camera/head_lidar/base_link
capture_timestamp：点云时间戳
对应时刻TF
ICP参数：体素大小、最大匹配距离、迭代次数等
```

输出建议定义为：

```json
{
  "ok": true,
  "method": "icp",
  "source_frame": "base_link",
  "object_model": "4317",
  "T_base_link_from_object": [[...], [...], [...], [...]],
  "converged": true,
  "fitness": 0.91,
  "rmse_m": 0.012,
  "inlier_ratio": 0.84,
  "point_count": {
    "model": 5000,
    "observed": 1800
  },
  "initialization": {
    "method": "obb_multistart",
    "candidate_count": 4
  }
}
```

数值仅用于说明字段，不代表当前性能。

## 核心区别

| 维度 | 当前 FoundationPose++ | 目标本机 ICP |
|---|---|---|
| 方法性质 | 学习式 RGB-D 6D 位姿估计 | 基于三维几何的迭代配准 |
| 对 RGB 的依赖 | 强 | 普通 ICP 无；彩色 ICP 有 |
| 对点云质量的依赖 | 中等 | 很强 |
| 对初始位姿的依赖 | 相对较低 | 很强 |
| 遮挡适应性 | 通常更好 | 点云残缺时容易漂移 |
| 对称物体 | 仍可能存在歧义 | 更容易陷入 180° 对称解 |
| 网络依赖 | 依赖工作站和网络服务 | 不依赖外部工作站 |
| 数据传输 | 需要传 RGB、深度和 mask | 数据留在机器人内部 |
| 延迟稳定性 | 受网络和服务排队影响 | 受 S1 本机算力和点云规模影响 |
| 部署复杂度 | 外部服务复杂 | 标定、点云处理和初值生成更复杂 |
| 输出可信度判断 | 服务成功和姿态格式检查 | 必须检查 fitness、RMSE、内点率和多初值一致性 |
| 主要风险 | 工作站/网络失效、模型服务版本漂移 | 初值错误、局部最优、稀疏点云、对称歧义 |

## ICP 不能直接“原样替换”的地方

最大差异是初始位姿。

FoundationPose++可以利用 RGB、mask、深度和学习特征寻找物体姿态；ICP本身只会回答：

> 给定一个已经比较接近的初始变换，怎样把模型点云进一步贴合现场点云？

所以目标链必须额外补上“粗初始化”：

```text
YOLO mask
  ↓
箱体点云
  ↓
质心 + PCA/OBB + 地面法向
  ↓
生成多个候选初值
  ↓
分别运行ICP
  ↓
选择RMSE低、内点率高且尺寸合理的结果
```

4317 箱体还存在水平面内的 180° 对称性。建议至少尝试：

```text
yaw
yaw + 180°
必要时再加入 yaw ± 90°
```

最后按照现有规则统一箱体语义长轴方向，否则左右机械臂可能发生互换或抓取方向翻转。

## 对下游代码的建议

为了让 ICP 替换尽量局部化，目标实现最好兼容现有姿态接口：

| 统一字段 | FoundationPose++来源 | ICP来源 |
|---|---|---|
| `object_in_camera` | FDP直接输出 | 将ICP结果变换到相机坐标系 |
| `object_in_world` | `T_base_camera × T_camera_object` | ICP若在 `base_link` 配准则直接输出 |
| `target_roi` | SAM3/ROI | YOLO26s-seg |
| `pose.method` | `foundationpose` | `icp` |
| `pose.quality` | FDP状态 | fitness、RMSE、内点率、初值一致性 |
| 目标生成输入 | 4×4 `T_base_object` | 保持相同的4×4 `T_base_object` |

这样后面的 Mode 00 语义轴转换、人工偏移、预抓、内收和提升逻辑暂时可以保持不变。

最终区别可以压缩成一句话：

> 当前 FDP++ 是“把完整感知数据交给工作站直接估计姿态”；目标 ICP 是“机器人先融合并分割出可靠箱体点云，再依靠粗初值和模型点云在本机完成几何精配准”。
