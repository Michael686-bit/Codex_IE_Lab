## 它实际用来做什么

它不是单纯的“抓一个箱子脚本”，而是面向连续拆垛的任务控制器：

```text
启动检查
→ 准备正面观察姿态
→ 导航到 Front
→ SAM/深度感知
→ 判断空垛、00、10、01 或不可抓
→ 执行对应抓取策略
→ 验证持箱
→ 选择卸货位
→ 持箱运输
→ 松爪
→ 复位
→ 返回 Front
→ 下一循环
```

它区分：

- `COMPLETED_EMPTY`：重新感知确认正面为空；
- `STOPPED_LIMIT`：达到循环上限，不代表空垛；
- `BLOCKED`：条件不足但没有不明确运动；
- `RECOVERY_REQUIRED`：可能已经运动、接触或持箱，必须人工恢复。

运行时不使用 ROS，主要通过：

- S1 SDK；
- 原生 IMC；
- SAM3/LingBot/FDP 外部服务；
- Docker 容器和宿主机 `control.lock`。

## 和旧版 `main_pipeline_s1_mode00.py` 的区别

### 旧版 mode00

旧脚本是一条写在单个 Python 文件里的单箱固定流程：

```text
定位/姿态
→ SAM 感知
→ 导航到观察位
→ FDP
→ 生成双臂目标
→ 双臂预抓
→ 内收
→ 合爪
→ 上抬 100 mm
→ 持箱导航
→ 高位松爪
→ 双臂和底盘回 SAM
```

特点：

- 单箱、单次执行；
- 流程主要硬编码在 `Mode00Pipeline.run()`；
- 通过 `docker exec` 调用多个工具；
- 参数大量来自 Python 常量和旧 JSON/YAML；
- 有每阶段人工确认、控制锁、制品校验和持箱状态文件；
- `put/down` 被明确禁用；
- 支持有限的“合爪后继续”恢复路径；
- 入口是：

```text
scripts/run_s1_mode00_one_click.py
→ import main_pipeline_s1_mode00
```

### 新项目中的 mode00

新项目把旧流程拆成多个可复用步骤：

```text
prepare_front_observation
→ navigate_front
→ survey_front
→ mode00_prepare_fdp
→ mode00_capture_fdp
→ mode00_lock_pose
→ mode00_build_targets
→ mode00_open_grippers
→ mode00_dual_pregrasp
→ mode00_dual_inward
→ mode00_close_dual
→ mode00_lift_dual
→ verify_carried
→ transport
→ release
→ reset_robot
→ return_front
```

主要变化：

- 从单体脚本变成 Mission 状态机；
- 配置从代码常量移到 `config/`；
- 每一步统一执行：

```text
machine_gate
→ plan
→ RUNNING 检查点
→ execute
→ verify
→ 完成回执
```

- 运动异常不会自动重放；
- 每一步的计划、执行、验证结果都写入带哈希的制品；
- 支持连续多循环；
- 同一套步骤可以用于 `mission`、`scenario` 和单步调试；
- `FakeAdapter`、`ReplayAdapter` 可以做离线测试。

所以，新项目不是简单复制旧的 `main_pipeline_s1_mode00.py`，而是对其行为进行重构和泛化。

## 和旧版 `main_pipeline_s1_mode10.py` 的区别

旧版 mode10 脚本的定位非常明确：它是路线设计/安全验证程序。

它定义了：

```text
右臂主抓
→ 右臂闭合
→ 右臂抬升并外拉
→ 左臂重新 FDP
→ 左臂安全过渡
→ 左臂补抓
→ 双臂抬升
```

但它的代码中：

```text
--execute
```

最终会主动抛出 `Mode10Refused`，不会连接 SDK，也不会执行真实动作。

它当时还有两个重要限制：

1. `right_extract` 把“抬升 + 外拉”合成一个阶段；
2. `left_safe_clearance` 仍然是 `blocked_pending_validation`。

新项目中，mode10 被接入了统一的顺序策略状态机：

```text
mode10_prepare_fdp
→ mode10_capture_primary
→ mode10_lock_primary
→ mode10_primary_pregrasp
→ mode10_primary_grasp_close
→ mode10_primary_lift
→ mode10_primary_draw
→ mode10_capture_secondary
→ mode10_lock_secondary
→ mode10_secondary_safe_clearance
→ mode10_secondary_pregrasp
→ mode10_secondary_contact
→ mode10_secondary_grasp_close
→ mode10_capture_achieved_tcp
→ mode10_dual_lift_to_level
```

关键变化：

- 旧版合并的 `right_extract` 被拆成：

```text
primary_lift
primary_draw
```

这样可以在抬升成功、外拉失败时准确停在外拉恢复点。

- 旧版的 `left_safe_clearance` 变成新项目中的独立 `secondary_safe_clearance` 步骤；
- 第二次 FDP、实际 TCP、双臂抬升都有单独证据；
- mode10 和 mode01 共用顺序抓取步骤类，但参数独立配置；
- 当前新项目的 mode10 已有后续实机回归记录，旧版 `main_pipeline_s1_mode10.py` 则属于更早的开发阶段。

## 两套项目的关系

关系可以概括为：

```text
旧项目：
现场实验脚本 + 已验证单箱流程 + mode10 路线草案
        ↓ 提取行为、参数、制品和安全经验
新项目：
独立的配置化、状态机化、可恢复连续拆垛控制器
```

具体联系：

- 新项目的 4317 mesh 和 IMC 配置来自旧工程的固定提交；
- 新项目的 mode00 行为基线参考旧版已验证流程；
- `config/robot/s1.yaml` 中的 mode00 FDP 姿态，明确追溯到旧版：

```text
main_pipeline_s1_mode00.py
FDP_OBSERVATION_POSE = fdp-mode10-taught-20260815
```

- 新项目的 replay fixture 使用旧项目运行制品的哈希作为历史回放证据；
- 旧 mode10 的路线设计和失败边界影响了新项目的顺序状态机设计。

但重要的是：

```text
s1_continuous_destack
不会在运行时 import 或调用
main_pipeline_s1_mode00.py / main_pipeline_s1_mode10.py
```

旧脚本现在主要是：

- 行为基线；
- 参数来源；
- 历史实机证据；
- 回放测试来源；

而不是新项目的运行依赖。

## 最核心的判断
