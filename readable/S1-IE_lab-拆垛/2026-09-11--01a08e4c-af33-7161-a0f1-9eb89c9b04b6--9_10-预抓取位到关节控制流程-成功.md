### 1. 表中的 TCP 位置如何计算

在：

`src/s1_sjtu/mode00_geometry.py:193-295`

设：

```text
c = 箱体中心位置
u = base_link +Z = [0, 0, 1]
a = 箱体长度方向投影到水平面的单位向量
```

代码先从箱体位姿提取水平接近轴：

```python
a = normalize(R[:, 0] - dot(R[:, 0], u) * u)
```

然后使用 4317 箱体尺寸：

```text
长度 = 0.4 m
宽度 = 0.3 m
高度 = 0.175 m
```

目标位置可简化为：

```text
左抓取位  = c + 0.21 * a + 0.0625 * u
右抓取位  = c - 0.22 * a + 0.0625 * u

左预抓取位 = c + 0.33 * a + 0.0625 * u
右预抓取位 = c - 0.34 * a + 0.0625 * u
```

其中：

```text
0.0625 = 0.7 × 0.175 + 0.010 - 0.070
0.33   = 0.21 + 0.12
0.34   = 0.22 + 0.12
```

所以你表里的 V5/FDP 数值正是这套几何公式的输出。例如 FDP 预抓取位置：

```text
left  = [0.973265,  0.317579, 0.603564]
right = [0.924421, -0.350638, 0.603564]
```

这些只是 TCP 笛卡尔目标，还不是关节角。对应的完整 TCP 姿态还包括旋转矩阵。

### 3. TCP 如何转换成关节姿态

预抓取阶段调用：

```text
main_pipeline_s1_mode00.py:1014-1016
```

最终执行：

```text
host_s1_imc_live_dual_plan.py
```

关键过程在：

`tools/host_s1_imc_live_dual_plan.py:329-547`

#### 读取实时关节作为 IK 初值

S1 的 whole-body 关节向量是 17 维：

```text
whole_body[0]     = torso_lift_joint1
whole_body[3:10]  = left_arm 7 个关节
whole_body[10:17] = right_arm 7 个关节
```

代码使用实时左右臂关节：

```python
current = whole[start:end]
```

然后读取：

```python
kin.getFK(current, -1)
kin.getFK(current, 0)
```

同时调用 S1 SDK 的 FK，比较 IMC 坐标系和 SDK `base_link` 坐标系，自动确定：

- IMC FK 是否已经是 `base_link`
- 是否需要乘以基座变换
- TCP/安装座之间的固定工具变换

因此它不是简单地把 `[x,y,z]` 送进 IK，而是使用完整的：

```text
位置 + 姿态 + 坐标系 + GE103 TCP 工具变换
```

#### 调用原生 IMC IK

核心代码是：

```python
goal = kin.getNearestIK(
    desired_imc,
    current,
    0.0
)
```

它返回单臂 7 维关节目标：

```text
goal_joint_rad = [joint1, joint2, ..., joint7]
```

这里的 IK 数值算法不在 Python 源码中，而是在外部原生模块：

```text
imc_interface_py
```

所以目前能够确认：

- 使用当前关节作为 seed；
- 调用 `getNearestIK`；
- 选择接近当前姿态的 IK 解；
- 具体是何种数值优化/Jacobian 算法，当前工程源码无法确认。

这条 one-click 路径也没有调用 `set_joint_positions`。同目录的 `host_mode00_pregrasp_sdk_runner.py` 虽然包含 SDK 直接 IK 逻辑，但不是这个 one-click 流程实际调用的主路径。

### 4. IK 结果如何变成运动轨迹

预抓取阶段使用：

```text
planning-method = ptp
sample-period = 0.01 s
planning-ratio = 0.05
```

调用：

```python
raw = solve_ptp(
    planner,
    current,
    goal,
    0.01,
    0.05,
    False
)
```

返回的是一串 7 关节 waypoint，而不是一个关节目标。

随后代码会：

1. 检查起点是否等于实时关节；
2. 检查终点是否等于 IK goal；
3. 检查所有 waypoint 是否在 URDF 关节限位内；
4. 左右臂独立规划；
5. 将左右路径重采样到相同点数；
6. 组合成每个时刻的 17 维 whole-body 状态；
7. 用 SDK 加载 GE103 工具模型检查双臂自身碰撞。

需要注意，IMC 规划时传入的 `check_collision=False`，碰撞检查是后续单独做的；而且当前碰撞场景没有加入真实箱体和环境障碍物，只能证明一定范围内的机器人/工具自碰撞检查。

### 5. 最终发送的机械臂控制命令

执行器：

`tools/host_s1_imc_dual_plan_executor.py:84-101, 196-214`

构造：

```python
trajectory.joint_groups = ["left_arm", "right_arm"]
trajectory.joint_names = []
```

每个轨迹点的关节顺序是：

```text
[left_arm 的 7 个关节] + [right_arm 的 7 个关节]
```

最后实际调用：

```python
robot.call(
    "execute_joint_trajectory",
    trajectory,
    True
)
```

其中 `True` 表示阻塞执行。

执行完成后还会读取左右臂反馈，确认：

- 轨迹状态为 `COMPLETED`；
- 关节误差在阈值内；
- 速度接近 0；
- 连续多个采样保持稳定。
