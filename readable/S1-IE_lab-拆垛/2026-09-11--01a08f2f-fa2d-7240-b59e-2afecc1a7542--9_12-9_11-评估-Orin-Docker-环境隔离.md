**我赞成。以后 S1 的 Orin 上新增算法实验，建议默认用 Docker 隔离。**这样 Python、NumPy、OpenCV 等依赖都装在镜像里，版本冲突或实验失败时可以重新构建、切回旧镜像，减少对现有环境的影响。

结合目前箱体定位流水线，我建议分两步迁移：

| 部分 | 建议 |
|---|---|
| S1 原厂服务、驱动、现有 SDK 环境 | 保留在宿主机 |
| 腕部 RGB-D、K、TF 采集 | 第一阶段沿用现有采集入口，向容器提供冻结数据 |
| SAM3/LingBot 客户端、ROI、V5、后续算法 | 放进 Docker |
| 原始数据、模型 | 只读挂载 |
| 实验结果、日志 | 写入独立实验目录，保留在容器外 |

**先做到“宿主机采集 → Docker 内计算 → 输出位姿”最合适。**先用已经归档的数据验证容器内结果与现有版本一致，再接实时采集；SDK 能否完整放进容器，后续单独验证。

不过 Docker 的隔离也需要配置：

- 不默认使用 `--privileged`，不把整个宿主机目录或 Docker socket 挂进去；可写挂载仍然能改动宿主机文件。[Docker 权限与挂载说明](https://docs.docker.com/engine/containers/run/)
- 设置 CPU、内存限制及日志轮转，避免实验争抢原厂服务的资源；Docker 默认没有资源上限。[资源限制说明](https://docs.docker.com/engine/containers/resource_constraints/)
- Docker **不隔离物理运动风险**，能连接控制接口的容器仍可能控制机器人，运动确认规则照旧。

我们 9 月 10 日的部署记录是 **JetPack 5.1.4 / L4T 35.6.0、ARM64**。后续如果用 GPU，需要核对对应镜像与 NVIDIA 容器运行时的兼容性，不能直接照搬 PC 的 CUDA 镜像。[NVIDIA Jetson 容器说明](https://nvidia.github.io/container-wiki/toolkit/jetson.html)

我的建议是：**把 Docker 作为后续实验的默认部署方式，先迁移感知计算部分，保留当前可用版本作为回退。**本次未连接 S1、未安装或修改环境；落地前还需只读检查 Orin 已有的 Docker 和 NVIDIA runtime 状态。
