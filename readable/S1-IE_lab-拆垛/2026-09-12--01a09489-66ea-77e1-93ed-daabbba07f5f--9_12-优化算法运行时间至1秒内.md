## 2. 助手（进展）

我先看一下“9_12 制定离线功能测试方案”的上下文和仓库记录，确认当前耗时在哪些环节，再判断如何在保留 Docker 环境隔离的同时压到 1 秒左右。

## 3. 助手（进展）

已有证据支持继续保留 Docker：同一帧只调整线程配置，容器就从 34.34 秒降到了 15.59 秒。剩下要争取约 16 倍加速，需要改计算过程。我在源码里确认了多初值逐个拟合、残差计算反复建最近邻树这两处值得优先测量的开销。

## 4. 助手

**可以继续用 Docker。我的建议是保留环境隔离，重点优化 V5 的计算过程，再把适合并行的部分搬到 GPU。** 目前不能保证能到 1 秒，但有几处明确值得动手的优化点。

前一轮的实际结果是：

| 同一帧计算 | 耗时 |
|---|---:|
| 原 `_03` 容器 V5 | 34.34 s |
| 容器 V5，调整 BLAS/OpenMP 为单线程 | **15.59 s** |
| 宿主机 V5 | 17.60 s |
| FDP 客户端请求 | **1.23 s** |
| FDP 服务内部报告 | 0.50 s |

所以，**没有必要为了速度放弃 Docker**。不过，从 15.59 秒压到 1 秒，还需要约 **16 倍加速**，仅调整线程或开启 GPU 访问权限不够。[已有测试记录](../../assets/cc6b470f56313926--s1_orin_docker_online_test_20260912.md)

我建议按以下顺序推进。

**1．先消除重复计算，尽量保持现有算法结果。**

源码里有一个很具体的机会：每次优化器计算残差，都会把模型点变换到当前位姿，**重新建立一棵反向最近邻树**。

可以改成：

> 模型点的树建一次 → 把观测点逆变换到模型坐标系 → 查询同一棵树。

在当前每次拟合选定模型点集不变、变换为刚体的条件下，两者的欧氏最近邻距离数学上等价；仍需要验证数值误差和最终结果。此外，观测点降采样、观测树、模型加载也有重复，可复用。**这是我最建议先做的一步。**

先分别测初始化、最近邻、优化器、歧义检查的耗时，才能知道这些改动实际能省多少。

**2．把“所有初值完整拟合”改成“粗筛＋少量精修”。**

当前这帧有 12 个初值，逐个优化，之后还有内外表面竞争检查。可以试验：

- 全部初值先用稀疏点云做少量迭代；
- 保留排名靠前且姿态不同的候选，做完整精修；
- 分数接近时扩大搜索，保留歧义拒绝能力。

不能简单只留第一个候选，否则可能把原本应拒绝的内外壁歧义变成错误接受。

另外，当前优化器使用数值差分，可评估显式导数，减少为估计导数而反复计算残差的次数。[SciPy 说明](https://docs.scipy.org/doc/scipy/reference/generated/scipy.optimize.least_squares.html)

**3．CPU 优化后仍不够，再做批量 GPU 后端。**

GPU 方案应把多个候选的点变换、距离计算和残差计算成批执行，尽量让数据留在 GPU。逐个小操作在 CPU/GPU 之间来回切换，可能吃掉收益；NVIDIA 也建议减少传输和合并小任务。[CUDA 优化指南](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/)

这可以全部放进**独立的新 Docker 镜像**，沿用已验证的宿主机驱动接口，算法依赖安装在容器内。原 `_03` 保留作对照。

同时采用**容器内常驻算法进程**，模型和缓存初始化一次，后续按请求计算。但它主要消除启动开销，不能直接解决已有的 15.59 秒算法耗时。

**我建议把目标定为：确认后的 Observation 就绪，到输出位姿或拒绝结果，预热后 P95 ≤ 1 秒。** 冷启动另外报告；采集、SAM3/LingBot 和人工确认不包含在这 1 秒内。先争取 5 秒、再到 2 秒、最后冲击 1 秒，这些是阶段目标，不是加速承诺。

下一步最有价值的是：**用已有冻结数据做分阶段计时，先实现固定 KDTree 和缓存复用，再与旧 V5 比较耗时、位姿及拒绝结果。** 这一步可以先在本地开展，保留 Docker 隔离，也无需重新采集机器人数据。

## 8. 助手

**两次用的是同一个 V5 算法、同一个 Docker 镜像、同一帧输入，区别在启动容器时的线程配置。**

| 项目 | 原运行：34.34 s | 调整后：15.59 s |
|---|---|---|
| 镜像、算法、输入 | 相同 | 相同 |
| CPU 配额 | 6 个 CPU 的计算配额 | 相同 |
| BLAS/OpenMP 线程数 | 未显式设置，使用库的默认策略 | 显式设为 1 |
| GPU 计算 | 没有 | 没有 |
| 输出 | accepted | accepted，中心不变 |

调整后，启动命令多了这四个环境变量：

```bash
--env OPENBLAS_NUM_THREADS=1 \
--env OMP_NUM_THREADS=1 \
--env MKL_NUM_THREADS=1 \
--env NUMEXPR_NUM_THREADS=1
```

**为什么线程少了反而更快？**

V5 里有大量反复执行的小规模计算。底层数学库如果为这些计算启动多个线程，线程之间的调度、同步，以及超过容器 CPU 配额后的等待，可能比实际计算还费时间。设置单线程后，这些开销减少了。

这里的“单线程”指这些底层计算库，**不是把容器的 CPU 配额改成 1，也不代表整个程序所有部分都只有一个线程**。

因此，这次变化是**运行配置优化，算法没有修改**。已有实测支持默认线程配置是慢速的重要因素，但尚未精确测出调度、同步和配额等待各占多少。[诊断记录](../../assets/cc6b470f56313926--s1_orin_docker_online_test_20260912.md)
