# 机器人端部署

**适用场景：** 生产环境部署，实时性要求高的应用

**特点：** 无网络延迟，通信开销最小

## 1. 连接机器人网络

1.1 开机后在网络选择界面连接WiFi





1.2 在Network界面查看机器人IP地址



**IP 用途说明**

此 IP 为后续部署 SDK 到机器人时需要输入的 IP 地址，外部也可通过 `ssh` 登录此 IP 在机器人上运行程序。同时，在进行 SDK 与机器人系统版本兼容性检查时，也可以通过该 IP 指定目标机器人：
```bash
galbot_sdk check-version [--robot-ip <IP>]
```

## 2. 部署SDK到机器人

2.1 在PC上执行部署脚本
```bash
cd GalbotSDK
./deploy_to_robot.sh
```

2.2 根据提示输入连接信息

- 用户名：`galbot`
- Orin IP地址：例如 `192.168.120.180`
- 密码：[REDACTED]

**部署结果**

动态库自动安装到：`/data/galbot/lib`

2.3 验证安装
```bash
ssh galbot@<机器人IP>
ls /data/galbot/lib | grep galbot_sdk
```

**预期输出**

显示 libgalbot\_sdk.so 和 libgalbot\_sdk.so.1.7.0

2.4 环境变量配置

**环境变量已自动配置**

使用 `deploy_to_robot.sh` 部署SDK时，安装脚本已自动配置环境变量并写入 `~/.bashrc`，重新登录或运行 `source ~/.bashrc` 即可生效。

如果运行程序时找不到 `galbot_sdk` 库，请执行：
```bash
export LD_LIBRARY_PATH=/data/galbot/lib:$LD_LIBRARY_PATH
export PYTHONPATH=/data/galbot/lib:$PYTHONPATH
export PATH=/data/galbot/lib/galbot_sdk/bin:$PATH
echo 'export LD_LIBRARY_PATH=/data/galbot/lib:$LD_LIBRARY_PATH' >> ~/.bashrc
echo 'export PYTHONPATH=/data/galbot/lib:$PYTHONPATH' >> ~/.bashrc
echo 'export PATH=/data/galbot/lib/galbot_sdk/bin:$PATH' >> ~/.bashrc
```

## 3. 运行程序

### 3.1 Python程序

3.1.1 传输python源码到机器人的Orin上
```bash
scp your_app.py galbot@<机器人IP>:/userdata
```

3.1.2 运行PYTHON程序
```bash
python your_app.py
```

### 3.2 C++程序

3.2.1 在PC上安装SDK

进入到SDK目录下执行安装脚本
```bash
cd GalbotSDK
./install.sh
```

3.2.2 在PC上交叉编译（aarch64）
```bash
cd examples/cpp/
mkdir -p build
cd build
cmake ../ -DCMAKE_TOOLCHAIN_FILE=../cmake/linux-aarch64-gcc940.cmake
make
```

3.2.3 传输可执行文件到机器人的Orin上
```bash
scp your_app galbot@<机器人IP>:/userdata
```

3.2.4 运行程序
```bash
ssh galbot@<机器人IP>
cd /userdata
./your_app
```

# PC端部署 - Ubuntu

**适用场景：** 开发调试，快速迭代

**特点：** 开发便捷，支持局域网远程控制

## 1. 物理连接

PC 通过以太网转接板与机器人相连。转接板用于把标准 RJ45 网线接口转换为机器人专用的以太网接口，使用步骤如下：

1.1 将网线一端插入转接板的 RJ45 接口，另一端连接到 PC 网口

1.2 将转接板的另一端插入机器人背部对应的以太网接口



连接完成后整体走线如下图所示：



## 2. 配置网络

### 2.1 配置PC网口IP

- IP地址：`192.168.1.99`（或同网段其他地址）
- 子网掩码：`255.255.255.0`

设置路径：**设置 → 网络 → 有线设置 → IPv4 → 手动**



验证配置：
```bash
ifconfig
```

**预期输出**

显示 `inet 192.168.1.99`



### 2.2 一键配置PC、XCU、HPU端IP

**前提条件**

PC、XCU、HPU 三者需能互相 ping 通

在SDK目录下执行 `configure_embosa_ip.sh` 脚本，配置PC端的IP（以 PC: 192.168.1.99、XCU: 192.168.1.66、HPU: 192.168.1.88 为例）：
```bash
./configure_embosa_ip.sh
```

脚本启动后依次提示输入以下信息：
```text
请输入配置的 PC IP: 192.168.1.99          # 必填
请输入配置的 XCU IP [默认 192.168.1.66]:  # 直接回车使用默认值
请输入配置的 HPU IP [默认 192.168.1.88]:  # 直接回车使用默认值
```

脚本将自动完成 PC、XCU、HPU 三端的 embosa IP 配置并重启各端 launcher。

## 3. 在PC上安装SDK

进入到SDK目录下执行安装脚本
```bash
cd GalbotSDK
./install.sh
```

**环境变量已自动配置**

安装脚本已自动在PC端配置环境变量，将以下内容写入 `~/.bashrc`：
```bash
source /opt/galbot/galbot_sdk/linux-x86_64-gcc940/setup.sh
```

重新登录或运行 `source ~/.bashrc` 即可生效。如果找不到 `galbot_sdk` 库，请重新执行安装脚本或检查 `~/.bashrc` 中的配置。

## 4. 编译程序

在PC上编译（x86\_64）
```bash
cd examples/cpp/
mkdir -p build
cd build
cmake ../ -DCMAKE_TOOLCHAIN_FILE=../cmake/linux-x86_64-gcc940.cmake
make
```

## 5. 运行程序

5.1 运行C++程序
```bash
cd /userdata  # 或程序所在目录
./your_app
```

5.2 运行Python程序
```bash
python your_app.py
```

**python相关库安装**

在运行python example时依赖一些库，所以请先运行下面的脚本保证相关库已安装：
```bash
cd GalbotSDK
./install_python_deps.sh
```

## 3. 助手

**建议选择“PC 端部署 + Docker 隔离环境”：PC 负责 GP001 遥操作、数据采集与存储，G1 负责执行控制；训练放在独立的 GPU 环境中。** 机器人端部署保留为后续优化或兼容性备选。

我已经找到并读取“检查G1网线网络连接”的可见记录，也检查了当前项目文件。该对话最近几轮未返回正文，所以下面会区分已经验证的情况和仍需确认的条件。

**这三种方案实际不是完全互斥的。**

机器人端、PC 端决定**程序在哪里运行**；Docker 决定**运行环境如何隔离**。因此，我们完全可以选择在 PC 上用 Docker 运行 SDK 和采集程序。官方 Docker 方案也要求先完成 PC 端网络配置。[官方 PC 部署说明](https://developer.galbot.com/docs/SDK/1.9.1/g1/zh/installation_pc_ubuntu/)

| 方案 | 对遥操作数采的价值 | 主要代价 | 本项目选择 |
|---|---|---|---|
| 机器人 Orin 运行 SDK 和应用 | SDK 靠近机器人内部控制系统，适合本地执行 | GP001 接在 PC 时仍需跨机通信；数采、依赖和存储都需在机器人上维护 | 保留为执行端备选 |
| Ubuntu PC 原生运行 | GP001、采集程序、文件都集中在 PC，调试直接 | SDK、Python、训练依赖容易相互影响 | 可用于兼容性排查 |
| **PC Docker 运行** | 集中采集，同时固定依赖版本、便于复现 | 需要处理串口映射、网络与 SDK Python 兼容性 | **推荐主方案** |

这里有个关键点：**机器人端部署不等于整条遥操作链路“零延迟”**。GP001 如果连接 PC，操作指令仍要从 PC 传到机器人；把程序搬上 Orin，也不能消除这部分通信。

**结合我们已经完成的工作，继续 PC Docker 路线最合适。**

- 网络对话中，你已经验证 `eno1 / 192.168.1.99` 能访问 `.66` 和 `.88`，各 3 次 Ping 无丢包、约 `0.3 ms`。这支持继续验证有线方案，但还不能证明 SDK 和相机流的端到端延迟达标。
- 项目已有 PC 容器配置：Ubuntu 22.04、Python 3.11、LeRobot 0.4.4、host 网络和 GP001 串口映射。
- **现有容器尚不包含 Galbot SDK**，不能把容器就绪理解成已经能控制 G1。[容器说明](<../../assets/21a7e32b1fa6abd2--README.md>)
- 机器人端已有 SDK 1.9.0 的只读验证记录；现有遥操作代码主要完成映射、预览和合成验证，完整真机遥操作数采尚未验收。[验证记录](<../../assets/cb33cf65b7da4566--READ_ONLY_VALIDATION.md>)

推荐的职责分配如下：

| 环节 | 放在哪里 | 做什么 |
|---|---|---|
| GP001 读取与映射 | PC 采集环境 | 读取主臂、标定方向比例、生成 G1 目标动作 |
| G1 接口 | 优先 PC SDK 环境 | 下发目标、读取真实关节和夹爪状态、接入相机 |
| 数据记录 | PC，写入挂载的数据目录 | 同步保存图像、状态、动作、时间戳和任务描述 |
| VLA 训练/微调 | 独立 GPU 环境 | 读取数据集、训练与评估 |
| 初期策略推理 | GPU PC | 将模型动作通过同一套 G1 接口执行 |

**SDK 和 LeRobot 不必强行装进同一个 Python 环境。** 当前 LeRobot 用 Python 3.11，机器人历史 SDK 环境是 Python 3.8；这不证明 PC SDK 不支持 3.11，但必须核实。若不兼容，就让 SDK 运行在其支持的独立环境，通过明确的进程接口与采集程序连接。LeRobot 官方支持通过自定义机器人适配器接入厂商 SDK，不过 Galbot G1 的适配仍需要我们完成。[LeRobot 硬件接入说明](https://huggingface.co/docs/lerobot/integrate_hardware)

**对后续 VLA 来说，最需要优先保证的是采集内容与时间对齐。**

每个训练样本至少需要：

- **观察**：相机图像、G1 实际关节状态、夹爪状态。
- **动作**：经过映射和限幅后，实际提交给 G1 的目标指令；另存 GP001 原始输入便于排查。
- **上下文**：任务语言描述、episode 边界、成功/失败标记。
- **时间信息**：采样与接收时间、动作发送时间，以及丢帧或异常记录。

只保存 GP001 角度，或只保存 G1 的实际运动轨迹，都不足以完整表达“模型看到什么、当时应该输出什么”。相机的获取方式和时间戳对齐，是目前选型之后必须验证的一环。

接下来按这个顺序推进：

1. **核对 SDK 1.9.0 与机器人 GBS 的兼容性，获取匹配的 x86_64 SDK 或官方镜像。** 不因文档标为 1.9.1 就直接升级；页面中的 1.7.0 库名、1.8.0 镜像也是示例，不能混着照抄。
2. **验证 PC 容器内 SDK 导入、只读状态和相机读取。** Ping 通不代表 embosa 配置及 SDK 通信已经完成。
3. **恢复并验证 GP001 实时输入，再完成受限真机遥操作。**
4. **录制一小批完整 episode，检查视频、状态、动作对齐并做训练读取验证，再扩大采集。**

如果 PC SDK 的兼容性或通信表现成为明确阻碍，再采用 **“PC 采集与训练 + Orin 上运行轻量 SDK 执行服务”**。这能复用已有机器人端 SDK，但会增加跨机协议与同步工作，因此作为备选更合适。

**当前选型可以定为：PC Docker 数采，有线连接 G1，训练环境独立；先打通完整数据闭环，再决定是否把执行或推理迁移到 Orin。**

1. **GP001 用 USB 连接 PC，G1 用以太网直连 PC。**

2. **明确让控制通信走 `192.168.1.x` 有线网络。**
   Wi-Fi 可以保留用于上网。SDK 的目标和回传 IP、embosa 配置都需要核对；旧程序如果仍连接 `10.34.216.136`，接上网线也可能继续走无线。

4. **把控制循环和视频编码、磁盘写入分开。**
   控制循环及时读取和发送最新目标，避免等待录像或写盘。训练单独运行，初期不要一边遥操作采集、一边占满同一台 PC 训练。

5. **测“操作到反馈”的延迟和抖动。**
   记录 GP001 采样、目标生成、SDK 调用、G1 状态回传的时间，重点看 P95/P99 延迟、最长停顿和状态新鲜度。跨机器时间戳需先对时，不能直接相减。

**就目前证据，优先把现有 PC 有线直控方案跑通并测量，最有把握，也最方便同步数采。**

### 1. 方案架构

```text
GP001 主臂
    │ USB
    ▼
PC：遥操作与采集环境（Docker）
    ├─ 主臂读取、标定、动作映射
    ├─ Galbot x86_64 SDK
    ├─ 图像 / 真实状态 / 动作同步记录
    └─ 数据写入 PC 挂载目录
    │
    │ 有线以太网
    ▼
G1：执行指令、回传状态与相机数据

采集数据 → 独立 GPU 训练环境 → VLA 模型
                                 │
                       后续通过同一 G1 接口执行
```

控制循环与视频编码、磁盘写入分开。SDK 与 LeRobot 的 Python 版本如果不兼容，使用独立进程环境连接。

### 2. 实施计划与验收条件

| 阶段 | 主要工作 | 完成标准 |
|---|---|---|
| **① 有线 SDK 接入** | 核对 PC `.99`、XCU `.66`、HPU `.88` 的实际配置；获取匹配的 x86_64 SDK；核对 SDK/GBS 兼容性；验证容器内状态读取 | SDK 通信确认走有线；持续读取真实状态，记录更新频率、延迟和异常 |
| **② GP001 实时输入** | 确认串口读取；校验关节顺序、单位、中立位、方向与比例 | 主臂输入连续可用；映射结果可解释；拔线和停流能被检测 |

### 3. 延迟目标

当前约 **0.3 ms 的 Ping** 只代表此前少量测试中的网络往返时间，不代表整条控制链路。

本方案将低延迟目标落实为以下指标：

| 指标 | 计划 |
|---|---|
| 通信路径 | SDK 指令与状态回传明确走有线网络 |
| 控制频率 | **以 50 Hz 作为初始验证候选**，最终依据 SDK 支持能力和实测确定 |
| 周期稳定性 | 记录控制周期 P50/P95/P99、最大停顿、超期次数 |
| 数据新鲜度 | 记录主臂输入年龄、机器人状态年龄，识别旧数据 |
| 持续运行 | 初步以连续运行 **30 分钟**作为稳定性验收窗口 |
| 断流处理 | 注入主臂断开、网络中断、程序退出场景，验证停止和恢复行为 |

50 Hz 对应每周期 20 ms，但**不意味着机器人必须在 20 ms 内完成动作**。应分别测量软件处理时间、状态回传时间和机器人实际响应。

此前的 300 ms TTL 只作为历史候选；有线实测后重新确定。

### 4. 数据目标

每条 episode 保存：

- **观察**：任务相机图像、G1 实际关节位置、夹爪状态。
- **动作**：映射和限幅后实际提交给 SDK 的目标；同时保留 GP001 原始输入。
- **时间**：采样、接收、指令发送时间，以及丢帧和异常记录。
- **任务信息**：语言描述、开始结束、成功/失败。
- **配置**：关节顺序与单位、标定参数、相机配置、软件版本。

**动作定义在正式采集前固定，并在训练和推理时保持一致。** 这样才能避免采集完成后因单位、关节顺序或动作语义变化而返工。

## 75. 助手

是的，应该先标定，再进行任何真机移动。当前我们完成的是“联合读取和目标预览”，还没有进入运动阶段。

这里需要做的是遥操作会话标定，不是让 G1 自动回零：

1. **读取真实 G1 起点**
   记录当前 7 个关节位置、限位、活动控制器和反馈时间戳。

2. **GP001 保持中立**
   操作者保持双臂自然中立，连续采集一小段数据，得到 `q_gp001_start`，检查抖动和稳定性。

3. **确认映射参数**
   固定关节顺序、单位、方向和比例。第一阶段只开放 `left_arm_joint7`。

4. **验证零点一致**
   中立 GP001 时，目标必须等于当前 G1 起点：

   `q_g1_target = q_g1_start + direction × scale × (q_gp001 - q_gp001_start)`

   因此中立状态下不能产生跳变。

5. **只读预览通过后，再做小幅真机动作**
   先在现场看护、急停可触达的条件下测试第 7 关节小范围运动，再扩大到整臂。

当前 G1 的部分关节接近或位于硬限位，不能执行自动回零或整臂初始化。标定必须以当前真实姿态为起点，不能用猜测的 `zero/home` 代替。

所以正确顺序是：

**状态读取 → GP001 中立标定 → 单位/方向确认 → 只读映射预览 → 单关节微动作 → 扩展遥操作。**

```text
真实 G1/XCU/HPU
      ↓ 有线网络
PC：eno1 / 192.168.1.99
      ↓ host 网络
Docker 中的 Galbot SDK
      ↓ get_joint_states()

```

文件中的数据含义：

- `positions_rad`、`velocities_rad_s`、`timestamps_ns`：G1 SDK 返回的真实左臂状态。
- `host_time_ns`、`host_monotonic_ns`：Docker 收到并记录该状态时的 PC 时间。
- 设备信息也来自真实机器人：G1，序列号 `R001GBDDAAAA0592`，固件 `GBS_1.17.0.0.rc7`。
- 全程只调用读取接口，没有运动命令。

但需要准确区分两个频率：

- **97.5 Hz** 是 Docker 在 PC 上调用状态读取接口的频率。
- 975 次读取中有 **375 次返回了相同的 G1 源时间戳**，所以实际约有 600 个不同的机器人反馈时间戳，约 **60 Hz**。

同样，P95 `10.39 ms` 表示 PC 读取循环的间隔，不是完整的“机器人到 PC 网络延迟”。报告中的反馈年龄 P95 约 `11.90 ms`、最大 `55.19 ms`，但因为 G1 和 PC 时钟存在约十几毫秒偏差，只能作为新鲜度参考，不能直接当作精确端到端延迟。
