## 2. 助手（进展）

## 3. 助手

**需要。扩展到整臂、双臂遥操作时，碰撞保护应当是控制链路的一部分。** 你说的前两类属于自碰撞，桌子和墙壁属于环境碰撞。

我看了当前代码：[j7_follow.py](/home/lsy03/文档/ChatGPT/VLA%20G1%20项目/teleoperation/j7_follow.py) 已经有角度范围、速度、反馈偏差和数据超时检查，**但没有几何碰撞检测**。这些检查不能保证手臂不会撞到东西；也不能在尚未核实的情况下，假设底层 SDK 已经提供了保护。

需要覆盖的内容可以分成三类：

| 风险 | 需要的处理 |
|---|---|
| 左右臂互撞 | 使用两臂实时关节状态，检查整条手臂及夹爪之间的距离，不能只检查末端 |
| 手臂撞本体 | 使用包含躯干、头部等结构的机器人碰撞模型，检查运动过程中是否接近本体 |
| 手臂撞桌子、墙壁 | 将桌面、桌腿、墙壁等加入环境模型，并确定它们相对机器人底座的位置 |

**建议把最终检查放在机器人侧、运动指令提交之前：**

`遥操作输入 → 映射/逆解 → 限位限速 → 碰撞检查与减速 → SDK 执行`

这里有几个关键点：

- **检查运动过程，而不仅是目标姿态。** 起点和终点都没有碰撞，中间路径也可能穿过障碍物；双臂需要一起预测。
- **接近障碍就减速，留足停止距离。** 余量要考虑当前速度、通信与计算延迟、实际制动能力和模型误差，不能等几何模型已经相交才停止。
- **阻止危险目标时，也要处理已经下发的运动。** 单纯不发送下一帧，不一定会让机器人停下来，需要验证底层取消轨迹或受控停止的行为。
- **模型要包含夹爪和抓取物。** 夹着长物体时，物体也可能先撞到桌子或另一条手臂。

实现上可以考虑 MoveIt 的碰撞检测能力；MoveIt Servo 官方支持根据自碰撞和环境碰撞接近程度缩放速度，但是否能接入我们现有 Galbot 控制接口，还需要做适配验证。[官方说明](https://moveit.picknik.ai/main/doc/examples/realtime_servo/realtime_servo_tutorial.html)

**对我们当前项目，我建议先做“自碰撞 + 固定桌子/墙壁”的保护，再扩展自由双臂遥操作。** 固定环境可以先人工测量，用盒体建模，不必一开始就接深度相机；如果底座、桌子或障碍物位置发生变化，就需要更新它们的相对位置。当前 J7 小范围测试的已有保护，不能直接视为整臂遥操作的碰撞安全保障。

### 1. 优先检查本机 SDK、示例和机器人部署文件

**目的：找到与我们实际 SDK、固件版本一致的能力证据。** 这一步通常比公开网页更直接。

搜索范围：

- Galbot SDK 的源码、接口文档、示例和版本记录。
- 已保存的机器人部署配置；必要时只读检查真机文件。
- URDF、SRDF、运动规划配置及碰撞几何文件。

关键词：

```text
collision / self_collision / collision_check
distance / proximity / safety
planning_scene / moveit / srdf
avoidance / motion_planning
```

重点回答：

- 有没有“输入关节角，返回碰撞状态或最小距离”的接口？
- 有没有支持环境障碍物添加、更新和删除的接口？
- 碰撞检查是在规划阶段运行，还是执行过程中持续运行？
- 我们使用的 `set_joint_positions()`、`publish_target()` 是否经过碰撞保护？
- 是否支持双臂联合检查？是否包含夹爪和抓取物？

**产出：接口名称、所在文件、版本、调用路径和适用范围。** 找到 `collision` 字样本身不算确认功能。

重点区分：

- 底盘导航避障和机械臂避障。
- 接触后触发的力矩保护和接触前的几何碰撞检查。

### 4. 如果官方方案不足，搜索替代方案

**目的：找到改动量和能力适合当前项目的技术路线。**

以下名称作为候选搜索对象，后续以官方文档核实：

| 候选方向 | 搜索词 | 核实目的 |
|---|---|---|
| 独立碰撞检测库 | `FCL robot self collision distance continuous collision`、`Coal collision library robot` | 能否保留现有 SDK，仅增加执行前检查 |
| 运动学与几何计算 | `Pinocchio collision distance geometry model` | 能否由实时关节状态得到各连杆位置及距离 |
| 完整规划框架 | `MoveIt PlanningScene collision checking`、`MoveIt Servo collision checking` | 能否同时处理机器人与环境，并接入遥操作 |
| 带约束的实时控制 | `robot teleoperation collision avoidance QP velocity damper` | 能否在接近障碍时调整运动方向，而不只是停止 |
| 其他规划方案 | `cuRobo dual arm collision motion generation` | 是否适合双臂、当前硬件及控制频率 |

每个候选都要核实：**模型支持、双臂支持、距离查询、路径检测、计算延迟、依赖环境、许可证及维护状态。**

尤其要区分：**碰撞检测库告诉我们“是否危险”，避障控制还需要决定“怎么减速、停下或绕开”。**

### 5. 对公开资料无法回答的部分，形成厂商问题单

**目的：消除最关键的接口语义不确定性。** 先整理问题，联系厂商另行安排。

建议直接询问：

1. 当前 SDK/固件是否提供自碰撞和环境碰撞保护？默认是否启用？
2. `set_joint_positions()` 与 `publish_target()` 是否经过这些检查？
3. 是否提供不执行运动的碰撞或距离查询接口？
4. 是否提供 G1 的 MoveIt 配置包、SRDF 和完整碰撞模型？
5. 双臂、夹爪和抓取物是否纳入检查？
6. 触发保护后，已提交轨迹如何取消，机器人如何停止？

最终搜索报告应给出**一张证据表和一个推荐方案**：

- **原生支持：** 用哪个接口、覆盖哪些风险。
- **MoveIt 可接入：** 缺哪些配置和桥接工作。
- **独立检测库可接入：** 如何加入现有遥操作程序。
- **仍未确认：** 哪些必须由厂商或后续验证回答。

搜索顺序建议严格按 **本地 SDK → 官方资料 → MoveIt → 替代库** 推进，先确认已有能力，再决定是否增加新框架。

1. Galbot 原生方案最值得优先验证

Galbot SDK 的 `GalbotMotion` 已提供：

- `check_collision()`：检查机器人状态是否发生自碰撞或环境碰撞，支持批量状态；
- `motion_plan()`、`motion_plan_multi_waypoints()`：带碰撞检查的单链、多链和双臂轨迹规划；
- `add_obstacle()`：添加 box、sphere、cylinder、mesh、point cloud、depth image；
- `attach_target_object()`、`attach_tool()`：把夹爪、工具或抓取物加入碰撞模型；
- `safe_margin`：为环境障碍设置安全距离。

Galbot 官方说明也明确指出，环境障碍必须由用户手动加入，`galbotMotion` 当前不会自动同步导航系统的实时点云地图；移动障碍物需要删除后重新添加。[G1 SDK 1.9.0 碰撞示例](https://developer.galbot.com/docs/SDK/1.9.0/g1/en/examples_python/)、[G1 SDK 1.9.1 API](https://developer.galbot.com/docs/SDK/1.9.1/g1/en/api_python_reference/)

当前脚本走的是低层控制路径：

- [j7_follow.py](/home/lsy03/文档/ChatGPT/VLA%20G1%20项目/teleoperation/j7_follow.py:437) 使用 `publish_target()`；
- [j7_follow.py](/home/lsy03/文档/ChatGPT/VLA%20G1%20项目/teleoperation/j7_follow.py:439) 使用 `set_joint_positions()`；
- SDK 对 `publish_target()` 的说明是“只做基础结构校验”，没有碰撞规划；
- 项目文档也明确写着 `set_joint_positions()` 没有环境碰撞检测承诺。[g1_arm_smoke_test/README.md](/home/lsy03/文档/ChatGPT/VLA%20G1%20项目/g1_arm_smoke_test/README.md:64)

因此，当前遥操作不能认为已经具备自碰撞或桌面避障保护。

2. G1 的 MoveIt 支持情况

Galbot 官方公开的 [galbot_one_golf_description](https://github.com/GalaxyGeneralRobotics/galbot_one_golf_description) 提供 URDF、MJCF、USD 和碰撞网格，官方包本身主要是机器人描述和 RViz 显示。它的 `package.xml` 只声明了 `ament_cmake` 和 `xacro`，[CMakeLists.txt](https://raw.githubusercontent.com/GalaxyGeneralRobotics/galbot_one_golf_description/main/CMakeLists.txt) 也没有 MoveIt 配置或 `ros2_control` 控制器。

所以目前应判断为：

- **有条件使用 MoveIt 做离线模型、碰撞检查和规划；**
- **没有证据表明 G1 官方提供开箱即用的 MoveIt 真机控制链；**
- 若要真机执行，需要自己制作 `moveit_config`、SRDF、双臂规划组、控制器配置，并编写 MoveIt 到 Galbot SDK 的桥接层。

MoveIt Servo 很适合实时遥操作：接近自碰撞或环境碰撞时会减速，碰撞时可停止。[MoveIt Servo 官方说明](https://moveit.picknik.ai/main/doc/examples/realtime_servo/realtime_servo_tutorial.html) 但它需要完整的 `robot_description`、PlanningScene、关节状态输入和硬件控制接口。

当前项目也还没有安装 MoveIt 或 `ros2_control`；而且本项目的 RViz 模型会主动删除 collision geometry，[model.py](/home/lsy03/文档/ChatGPT/VLA%20G1%20项目/g1_rviz_sim/g1_rviz_sim/model.py:72)，所以现有 RViz 仿真不能直接用于碰撞验证。

3. 其他可选库

| 方案 | 能力 | 缺口 |
|---|---|---|
| GalbotMotion | 自碰撞、环境碰撞、障碍物、双臂规划 | 没有实时环境自动更新；高频低层命令不经过它 |
| MoveIt Servo | 实时碰撞监测、接近减速、碰撞停止 | 需要自己补齐 G1 的 MoveIt 和控制器桥接 |
| Pinocchio + Coal | 从 URDF 建立几何模型，计算自碰撞、环境碰撞和最小距离 | 只有检测能力，需要自己实现轨迹采样、减速和停止 |
| 直接 FCL/Coal | 底层几何碰撞和距离计算 | 不负责机器人运动学和执行控制 |

[Pinocchio 的几何模型和碰撞接口](https://docs.ros.org/en/rolling/p/pinocchio/doc/a-features/d-model.html)支持 URDF 几何模型和距离计算；[Coal](https://github.com/coal-library/coal) 是 HPP-FCL 的后续项目，支持碰撞、距离和安全余量。

我的推荐顺序是：

1. 先用 `GalbotMotion` 做 G1 原生碰撞检查；
2. 将桌子、墙壁建成 box 障碍物，并设置安全余量；
3. 遥操作每个目标段先经过碰撞检查，再提交运动；
4. 如果原生检查延迟或无法实现实时减速，再评估 MoveIt Servo；
5. 如果只需要轻量检测服务，再使用 Pinocchio + Coal。

下一轮最有价值的验证是一个**只读 G1 碰撞探针**：读取当前全身状态，调用 `check_collision()`；加入一个虚拟桌面 box，测试安全余量、双臂状态和调用延迟；全程不发送运动命令。需先核对真机 SDK 1.9.0 与本机 PC SDK 1.9.1 的版本匹配。
