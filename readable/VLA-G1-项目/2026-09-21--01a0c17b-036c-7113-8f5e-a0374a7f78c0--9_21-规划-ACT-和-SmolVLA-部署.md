| 模型 | 我的建议 | 在项目里主要验证什么 |
|---|---|---|
| **ACT** | **第一优先部署** | 用自己的示教数据，验证相机、关节状态、动作标签和控制链路能否学出稳定操作 |
| **SmolVLA** | **紧接着部署** | 测试轻量 VLA 微调，以及语言条件在任务中的作用 |
| **LingBot-VLA** | 保留现有环境 | 作为较大预训练模型的对照，判断额外算力是否带来实际收益 |

**ACT 特别适合当第一条基线。** 标准 ACT 是视觉模仿学习策略，不具备 VLA 那样的语言条件能力；通常要用自己的任务数据训练。它计算需求较低，也能帮助我们缩小排查范围：如果简单抓放任务都学不好，就优先检查数据、时间对齐和动作定义。LeRobot 官方也将 ACT 推荐为入门首选，并且基础安装已包含 ACT。[ACT 官方文档](https://huggingface.co/docs/lerobot/act)

**SmolVLA 则适合承接下一步。** 官方基础模型约 450M 参数，输入包括多视角图像、机器人状态和语言指令，支持在 LeRobot 数据上微调。官方建议以约 50 条任务示教作为起点，但这不代表 50 条就一定足够，也不能把基础权重直接当成适配好 G1 的策略。[SmolVLA 官方文档](https://huggingface.co/docs/lerobot/smolvla)

部署上，我建议：

- 新建一个与 LingBot 隔离的 **LeRobot 环境**，固定代码版本，先让 ACT 和 SmolVLA 共用。
- 先验收模型加载、GPU 推理、少量训练步和权重保存／重载。
- 再用**同一份 G1 数据、相同相机输入和动作定义**做对照，统一记录成功率、推理延迟、显存和动作平滑性。单任务操作能力与语言泛化能力分开评估。

其他模型我会放到第二阶段：

| 候选 | 推荐理由 | 当前取舍 |
|---|---|---|
| **π0.5 / OpenPI** | 增加另一套预训练 VLA 对照 | 官方估计推理需 >8GB、LoRA 微调需 >22.5GB 显存；4090 做微调余量紧，要按配置实测。[官方仓库](https://github.com/Physical-Intelligence/openpi) |
| **GR00T** | 官方当前版本包含真实 G1 评估，对我们的平台有参考价值 | 官方要求推理 16GB+，微调推荐 40GB+；适合后续有更大显存资源时加入，仍需适配我们的相机和末端执行器。[官方仓库](https://github.com/NVIDIA/Isaac-GR00T) |

**我倾向于这轮先把 ACT 和 SmolVLA 环境补齐，然后集中完成一个简单抓放任务的训练与闭环。** 当前最值得投入的是让这三个模型能用同一批数据公平测试。

## 4. 用户

ACT环境和SmolVLA环境是新建立一个 DOCKER 还是怎么部署比较好？

## 5. 助手

**建议新建一个独立的 LeRobot Docker 镜像，ACT 和 SmolVLA 共用这个镜像；与现有 LingBot Docker 分开。** 这比较适合我们现在的测试阶段。

ACT 已包含在 LeRobot 基础安装中，SmolVLA 只需在此基础上安装对应依赖，所以暂时没必要为它们各维护一套环境。[ACT 文档](https://huggingface.co/docs/lerobot/act)、[SmolVLA 文档](https://huggingface.co/docs/lerobot/smolvla)

建议按这个结构组织：

```text
4090 工作站
├── LingBot Docker            现有环境
└── LeRobot Docker 镜像       新建，固定依赖版本
    ├── ACT 容器 / 训练任务
    └── SmolVLA 容器 / 训练任务

宿主机挂载目录
├── datasets/                 共用数采数据
├── checkpoints/act/          ACT 权重
├── checkpoints/smolvla/      SmolVLA 权重
├── cache/huggingface/        模型下载缓存
└── outputs/                  日志和评估结果
```

这里的区别是：**镜像负责保存软件环境，容器负责运行具体任务。** ACT 和 SmolVLA 可以从同一镜像启动各自的容器，分别保存配置、权重和日志；以后确实出现依赖冲突，再拆成两个镜像。

具体部署时，我建议做到：

- **锁定版本**：固定 LeRobot commit、PyTorch/CUDA 和依赖版本，方便复现。
- **数据放在宿主机**：通过目录挂载供容器使用，删除或重建容器也不会丢掉数据与权重。
- **GPU 按需使用**：4090 上先轮流训练和测试，避免与 LingBot 常驻推理争抢显存。
- **先部署在工作站**：G1 侧沿用采集与控制程序，模型通过接口接入；后续统一三种策略的输入输出。

因此，这轮最合适的是：**增加一个 LeRobot Docker 环境，提供 ACT、SmolVLA 两套启动与训练配置。** 维护成本低，也方便后面做同数据、同任务的对照实验。

|---|---|---|

## 二、部署架构

**新增一个 LeRobot 基础镜像，ACT 和 SmolVLA 分别启动容器或运行任务。** 现有 LingBot 环境保留。

```text
4090 工作站
│
├── 现有 LingBot Docker
│
└── 新建 LeRobot Docker 镜像
    ├── ACT 训练 / 推理容器
    └── SmolVLA 训练 / 推理容器
         │
         └── 挂载宿主机目录
             ├── 数据集
             ├── 模型缓存
             ├── 训练权重
             └── 日志与评估结果
```

具体原则：

- 固定 LeRobot 代码版本、基础镜像及主要依赖版本。
- 优先共用镜像；如果验证发现依赖冲突，再拆分。
- 数据、模型权重、缓存、日志都保存在宿主机。
- 训练和性能测试默认按模型串行执行，避免争抢 4090 显存。
- 本轮容器不需要访问机器人控制设备。

## 三、实施步骤与验收标准

### 第 1 步：检查现有环境，确定兼容组合

检查以下信息：

- GPU 型号、显存、驱动版本及当前显存占用。
- Docker 和 NVIDIA Container Toolkit 是否能正常使用 GPU。
- 磁盘空间、模型缓存位置和下载连通性。
- LingBot 容器的挂载、端口与资源使用情况。
- 所选 LeRobot 版本对 Python、PyTorch、CUDA 和视频解码依赖的要求。

**产出：** 环境检查记录、版本选型表、目录与资源规划。

**验收：** 确定一组能够在当前驱动下运行、同时支持 ACT 和 SmolVLA 的依赖版本；明确新环境与 LingBot 不冲突。

### 第 2 步：构建 LeRobot Docker 镜像

镜像中安装：

- GPU 版 PyTorch。
- 固定版本的 LeRobot。
- ACT 所需依赖。
- SmolVLA 所需额外依赖。
- 数据读取、视频解码和基础诊断工具。

配置宿主机目录挂载、用户权限和模型缓存，避免容器生成的文件只能由 root 操作。

**产出：** `Dockerfile`、Compose 配置、版本锁定记录。

**验收：**

- 镜像构建成功。
- 容器内 CUDA 可用，能够完成实际 GPU 张量运算。
- ACT、SmolVLA 模块导入成功。
- 容器重建后，挂载的数据和输出仍然可用。

### 第 3 步：完成 ACT 最小验证

ACT 分成推理和训练两部分验证：

1. 按测试数据的图像、状态和动作维度初始化模型。
2. 用测试输入执行 GPU 前向推理。
3. 使用小型、可读取的样例数据集运行短训练。
4. 保存 checkpoint，并在新进程中重新加载。
5. 用重载后的模型再次推理。

这里可以使用预训练视觉骨干，但不能把初始化的 ACT 策略当作已训练好的 G1 策略。

**产出：** ACT 配置、测试脚本、测试 checkpoint 和日志。

**验收：**

- 动作张量形状正确，输出不包含 NaN/Inf。
- 训练前向、反向传播及参数更新正常。
- 权重保存与重载成功。
- 记录测试配置、显存和推理延迟。

### 第 4 步：完成 SmolVLA 最小验证

1. 下载并缓存选定版本的基础权重。
2. 验证图像、机器人状态、语言指令的预处理。
3. 执行 GPU 推理，检查动作输出。
4. 使用小型样例数据运行短微调。
5. 保存并重载微调结果。
6. 验证权重缓存可以被新容器复用。

**产出：** SmolVLA 配置、权重版本记录、测试脚本和日志。

**验收：**

- 基础权重完整加载。
- GPU 推理及短微调正常。
- 动作形状正确，输出不包含 NaN/Inf。
- checkpoint 重载成功。
- 记录显存、延迟及实际训练配置。

短训练只用于验证训练链路，不用于判断任务成功率。

### 第 5 步：统一使用入口与测试记录

提供 ACT、SmolVLA 一致的操作入口，支持：

| 操作 | 用途 |
|---|---|
| 构建环境 | 构建固定版本镜像 |
| 检查环境 | 检查 GPU、依赖和挂载目录 |
| 推理自检 | 验证模型加载和动作输出 |
| 短训练测试 | 验证完整训练链路 |
| 正式训练 | 使用指定数据集和配置训练 |
| 权重评估 | 加载指定 checkpoint 执行测试 |

性能记录统一包含：模型及代码版本、输入尺寸、相机数量、batch size、精度、动作块长度、GPU 显存和推理延迟。延迟统计区分首次加载、预热和稳定运行。

**产出：** 启动脚本、中文使用说明和部署验收报告。

**验收：** 按文档能够从新容器重复完成两个模型的最小验证，不依赖临时手工修改。

## 四、提前明确 G1 数据接口

本轮整理接口要求，下一轮结合真实数采结果落实。以下字段必须统一：

| 项目 | 需要确定的内容 |
|---|---|
| 相机 | 相机名称、数量、分辨率和图像时间戳 |
| 机器人状态 | 左右臂关节顺序、夹爪字段、单位 |
| 动作 | 关节目标或末端目标；绝对量或增量；夹爪定义 |
| 时间 | 采样频率、图像与状态对齐方式、动作对应时刻 |
| 任务 | episode 划分、任务文本、成功或失败标记 |
| 数据划分 | 按 episode 划分训练与验证集，避免相邻帧泄漏 |
| 归一化 | 使用训练集统计量，并与 checkpoint 一起保存 |

**尤其需要核实动作标签的来源：遥操指令、发送给机器人的目标值和实际反馈状态不能未经定义就混用。** 这会直接影响训练结果。

共用同一份原始数据，并不要求三个模型使用完全相同的预处理；各自的转换方式需要记录清楚。
