# 排查中州韵输入法失效

## 1. 用户

我现在使用的中州韵输入法有时有会自动失效需要 重新启动，这是为什么，帮我检查一下

## 2. 助手（进展）

我先检查系统里中州韵所依赖的输入法框架（通常是 Fcitx/IBus）、当前进程状态、用户会话日志和崩溃记录。先只做读取诊断，不改配置或重启服务。

## 3. 助手（进展）

目前确认是 Ubuntu 22.04 + X11，使用 Fcitx5 5.0.14 和 Rime 1.7.3。环境变量指向 Fcitx5，但沙箱里的进程视图看不到桌面会话进程；我继续核对启动项、配置冲突、Rime 部署日志，以及系统是否记录过崩溃。

## 4. 助手（进展）

日志给出一个很关键的方向：Fcitx5 主进程从 8 月 22 日一直存活，近期没有 core dump，也没有被 OOM 杀死；因此“失效”不像是整个程序崩溃，更像是输入上下文/前端与某些应用断连，或 Rime 模块卡住。日志里的 Wayland 连接失败在当前 X11 会话中属预期，不是主因。接下来我会筛出重载前后的异常，并运行官方诊断脚本检查 GTK/Qt 模块与 D-Bus。

## 5. 助手

检查结果：中州韵本身没有崩溃，更可能是 Fcitx5 与 GNOME/IBus 的输入连接偶尔失去同步。

依据：

- Fcitx5 主进程已连续运行约 10 天，没有退出、OOM 或 core dump。
- Rime 模块可以正常加载，配置中也未发现 YAML 错误。
- 失效后“重新启动输入法”实际上是在同一进程中重新加载前端和 Rime，所以会恢复。
- 当前累积了 **112 个输入上下文**，其中不少来自 LibreOffice、VS Code、终端等旧窗口。长时间不注销并频繁开关应用，比较容易留下失效连接。
- GNOME 仍保留 `IBus libpinyin` 的历史输入源，并在每次 Fcitx 重载时记录：
  `Unknown interface org.freedesktop.IBus or property Engines`
  说明 GNOME 的 IBus 管理器与 Fcitx5 的兼容接口存在冲突/不同步。
- 当前键盘布局是 `cn+altgr-pinyin`，重载时 GNOME 还会报告多项按键绑定被覆盖。这种布局与 Rime 叠加没有必要，通常使用普通 `us` 键盘布局更稳定。
- GTK2 的 Fcitx5 模块没有安装；若问题只发生在较老的软件中，这就是直接原因。
- 你的版本也比较旧：Fcitx5 5.0.14、fcitx5-rime 5.0.11、librime 1.7.3。

建议按优先级处理：

1. 把 GNOME 系统“键盘/输入源”只保留普通“英语（美国）”，中文输入完全交给 Fcitx5/Rime。
2. 清理遗留的 IBus `libpinyin` 最近使用记录。
3. 把 Fcitx5 两个分组统一为 `us` 布局，避免 `cn-altgr-pinyin` 与 Rime 叠加。
4. 如果使用老 GTK2 软件，安装 `fcitx5-frontend-gtk2`。
5. 为 Fcitx5 增加崩溃自动拉起机制；虽然这次没有发现崩溃，但可以避免将来真正退出后必须手动启动。
6. 长时间不注销的会话，偶尔注销再登录可清掉积累的输入上下文。

目前可以判断：**主因更偏向 GNOME/IBus/Fcitx 前端状态冲突，而不是中州韵词库或配置损坏。** 我这轮只做了检查，没有修改你的系统设置。
