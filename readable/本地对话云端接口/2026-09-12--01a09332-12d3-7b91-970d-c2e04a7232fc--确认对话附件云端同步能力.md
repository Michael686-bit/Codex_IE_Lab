四、升级资源识别与收集

资源识别不能只扫描 Markdown 链接，还要检查对话记录中的结构化图片和附件字段。

按以下规则处理：

- 文字表格：保留原有 Markdown 内容。
- 用户上传图片、助手生成图片：查找实际文件或可提取的嵌入图像，保存原始资源。
- Excel、CSV、PDF、Word、PPT 等附件：保存可找到的原文件，保留有意义的文件名。
- 工具生成的图表和文件：从明确关联的工具结果中提取资源引用；不把全部工具原始输出直接公开归档。
- 本地文件链接：解析真实路径，判断是否属于该对话的附件或交付成果。
- 普通提及的代码目录、系统路径、工作区路径：保留为上下文，不递归复制整个目录或整个项目。
- 外部网页链接：保留网址，不默认抓取整站内容。
- 外部图片和临时下载链接：仅对与对话明确相关、可访问且适合归档的资源尝试保存；遵守来源和工具的下载限制。
- 已丢失、已过期、权限不足或位于不可访问远程主机的文件：记录具体原因，不伪造替代文件。
- 交互可视化：可获得完整 HTML 及依赖时保存；仅有截图时标注为静态预览；无法恢复交互行为时明确说明。

不自动登录机器人或其他远程主机搜集文件，也不因消息提到某个路径就复制其中所有内容。

五、建立清晰的归档结构

建议沿用现有目录，新增：

- `assets/`：图片和附件，以内容哈希去重。
- `catalog/assets.json`：资源来源、类型、大小、哈希、保存位置及关联对话。
- `catalog/link_report.json`：链接分类与检查结果。
- `reports/sync_report.md`：本次更新和完整性报告。

资源映射应支持多个对话引用同一文件，避免重复上传。相同文件名但内容不同的资源不得互相覆盖。

先在临时目录生成新归档并检查，确认成功后再更新正式目录。保留无法重新读取来源的既有归档，并标明状态，避免因源记录暂时缺失而删除历史资料。

六、改写图片和附件链接

1. 将已收集资源的本地绝对路径改成指向 `assets/` 的相对链接。
2. 图片使用可显示的 Markdown 图片语法。
3. 附件使用可下载的 Markdown 链接。
4. 正确处理中文、空格、括号和特殊字符。
5. 只修改已识别的资源引用，不全局替换普通叙述或代码示例中的路径。
6. 不存在的资源保留上下文，并添加明确的“附件未归档”说明。
7. 如果现有引用标记只有内部编号、没有网址，不编造链接；可从来源元数据恢复时再补全。

七、检查遗漏和失效链接

本地完整性检查：

- 每个已改写的图片或附件链接必须指向实际存在的文件。
- 每个资源的文件大小和哈希应与复制结果一致。
- 每条识别出的资源引用都必须有状态：已归档、外部引用、缺失、不可访问或明确排除。
- 报告损坏记录、解析失败、空消息及无法识别的资源类型。
- 检查是否仍有应当改写的本地附件路径。

外部链接检查：

- 对外部 HTTP/HTTPS 链接去重后检查，设置超时和限速。
- 区分可访问、重定向、需认证、禁止访问、超时和明确不存在。
- 不把所有 403、超时或自动化访问受限都认定为链接失效。
- 对内网地址、带凭据或签名参数的链接，不默认请求；标记为未检查或特殊访问。
- 外部链接检查仅代表本次执行时的结果，不保证永久有效。

八、上传内容边界

继续排除登录凭据、认证文件、原始数据库、系统或开发者指令、隐藏推理，以及整份工具和终端原始日志。

正文沿用并检查现有脱敏规则。对于附件：

- 对文本类附件进行适当的凭据检查。
- 不宣称自动扫描能够发现图片或二进制附件中的所有敏感信息。
- 对明确含凭据的资源，生成适合归档的副本或排除并记录原因。
- 不修改原始附件。

上传前统计文件总量和最大单文件大小，核对 GitHub 当前限制。大文件不得静默跳过；若不能直接入库，优先评估同一仓库的附件发布方式，并在报告中说明存储位置。需要付费或引入其他存储服务时再询问用户。

2. 含用户上传图片的对话。
3. 含助手生成图片或图表的对话。
4. 含本地附件链接的对话。
5. 含中文、空格和特殊字符路径的对话。
6. 同名不同内容、不同名相同内容的资源。
7. 缺失文件、过期链接等异常情况。

针对解析、去重和链接改写增加必要测试，再执行全量导出。检查图片可以解码、关键附件可以打开，并抽查实际渲染效果。

8. 抽查 GitHub 中的对话页面、图片和附件链接；若无法完成云端展示检查，明确报告限制。

本次授权范围包含完成后的正常提交和推送，不需要再为同一上传动作重复询问。遇到无法自行解决的认证问题、付费需求或破坏性冲突时，说明具体阻碍。

十一、验收标准

必须达到：

- 已更新到本次执行截止时间可读取的对话。
